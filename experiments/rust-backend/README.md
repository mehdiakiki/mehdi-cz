# Rust backend labs

Eight small investigations accompany the reviewed articles listed in
`docs/editorial/rust-backend-eight-2026-10-26.json`.

The existing Content safety workflow runs these examples in its PostgreSQL job.
The same configured PostgreSQL service supplies disposable fixture data. Each
database test uses a separate schema. The lab pins dependencies in Cargo.toml
and commits the lockfile generated by GitHub CI.

| Article          | Fixture             | What it observes                                                                                 |
| ---------------- | ------------------- | ------------------------------------------------------------------------------------------------ |
| Axum rejections  | tests/http.rs       | A strict extractor skips the handler; custom errors retain status and JSON shape, including 413. |
| Middleware order | tests/middleware.rs | Router layers and ServiceBuilder with a paused Tokio clock.                                      |
| Process shutdown | tests/shutdown.rs   | A real child process receives SIGTERM with an HTTP request in flight.                            |
| Trace context    | tests/tracing.rs    | Span ancestry around an actual PostgreSQL query with and without propagation.                    |
| Column migration | tests/migration.rs  | Old/new SQL shapes, stale backfill, and the precise NOT NULL failure.                            |
| Sessions         | tests/sessions.rs   | Two pools observe revocation, expiry, and a store failure.                                       |
| Upload cleanup   | tests/uploads.rs    | Files and database state after cancellation, publication, and repeated deletion.                 |
| Job generations  | tests/leases.rs     | Guarded renewal, forced expiry, and stale attempts to save an effect.                            |

All build, test, formatting, and dependency-resolution commands run through
GitHub Actions under this repository's execution policy. Select Content safety
on the article branch. The PostgreSQL artifact preserves the test output and any
formatting or lockfile patch required for the commit.

The shutdown fixture is Linux/Unix-specific and uses loopback HTTP. Its stdin
control is a test mechanism. The bearer credentials in the router fixtures are
not production authentication.
The migration test exercises query compatibility, not a full rolling deployment.
The tracing capture has no OTLP exporter. The upload fixture uses local files,
not an S3 multipart service, and begins after a complete object is stored. The
job fence protects a local PostgreSQL effect; it cannot undo an external action.

Article snippets are extracted from marked source regions. The content check
requires those snippets to match the compiled fixture code. Keep the markers
when editing the lab or updating the manuscripts.

## Connection lifetime and retrieval investigations

`tests/pool_lifetime.rs` compares a checkout held across a gated dependency with
a checkout returned before that dependency completes. A one-slot pool makes
ownership observable. The tests also await cancellation and inspect a quote
update's affected rows after the input revision changes. The 200 ms acquisition
timeout is a fixture mechanism, not a performance result or production default.

`tests/retrieval_contract.rs` uses the configured pgvector extension and a small
corpus with tenant, deletion, revision, and embedding-model boundaries. It
compares an incomplete query with the serving query, checks late embedding
publication after edits and deletion, and inspects bounded context construction.
The vectors are synthetic. There is no external embedding or language-model
call, relevance benchmark, approximate index, or deployed-role RLS test. The
serving guarantee is tied to the retrieval statement's snapshot; it does not
recall text that was already sent to a provider.

The existing PostgreSQL job discovers both files through `cargo test
--all-targets`. Retain its artifact and source SHA before treating any planned
assertion as an observed result. These manuscripts follow the existing review
and publication controls.

Selected observed outputs are saved in [results/observations.txt](results/observations.txt).
The file links to the exact GitHub run and source revision. Virtual milliseconds
in the middleware example are test-clock values, not performance measurements.

## Filtered search and CI review evidence

`tests/pgvector_filter.rs` builds a real HNSW index over 1,010 synthetic vectors.
It checks the actual plans for exact, limited approximate, and iterative search
under the same tenant predicate. An authorized exact fallback preserves the
five-result serving requirement when approximate results remain short.
Its result counts describe this constructed
case, not a corpus relevance or capacity benchmark.

`tests/agent_review_evidence.rs` checks the rules for preparing an advisory
review packet from trusted-run stand-ins and synthetic proposals. It covers
stale source identity, a changed requirement harness, missing or unsuccessful
checks, unfinished agent runs, malformed or excessive output, and valid
positive cases. Command construction is inspected without launching Claude.
These tests do not authenticate a GitHub artifact, implement the vendor result
adapter, or measure the quality of live AI reviews.

## PostgreSQL rows through a slow HTTP download

`tests/http_row_stream.rs` uses a real Axum HTTP/1.1 response and a loopback TCP
client that reads one record, then pauses. A socket wrapper observes an actual
pending write before the test probes the one-slot database pool. The comparisons
keep a SQLx row stream checked out, release checkouts between bounded pages,
resume and validate the complete response, or disconnect and join the producer.

Fixed 4,096-byte records make the payload allowance meaningful before fetching.
Reservations follow owned `Bytes` through the HTTP stack; cleanup checks return
all permits and run another database query. This counts owned payload, not total
process or database-driver memory. Small socket buffers arrange the test; the
results are not production throughput measurements or an export snapshot policy.
The existing PostgreSQL job discovers all three cases through its normal backend
test command. Inspect that run before calling the planned checks observations.
