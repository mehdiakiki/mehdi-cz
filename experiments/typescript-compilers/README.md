# Three TypeScript compilers on the same code

Evidence for the article [Three TypeScript Compilers on the Same Code](https://www.mehdi.cz/blog/three-typescript-compilers-on-the-same-code).

The subject is this website at commit `703cb49`: a Next.js 16.3.4 project with 94 `.ts` and `.tsx` files (plus `.next/types/validator.ts`, generated by `next typegen`). Four compilers type check it:

| Name in the results | Package | What it is |
| --- | --- | --- |
| `tsc6` | `typescript@6.0.3` | the last compiler written in TypeScript, run by Node.js |
| `tsc7` | `typescript@7.0.2` | the Go port, stable release |
| `tsc7.1` | `typescript@7.1.0-dev.20260930.4` | the Go nightly that tsrs 0.18.0 follows |
| `tsrs` | `tsrs@0.18.0-ts7.1.0-dev.20260929` | the Rust port, experimental |

`tsrs --version` prints `Version 7.1.0-dev.20260930.4 (tsrs 0.18.0-ts7.1.0-dev.20260929, microsoft/TypeScript@b85298b6a81f)`. The npm package `typescript@7.1.0-dev.20260930.4` was built from commit `9adc871`, the next commit after `b85298b6` in microsoft/TypeScript. That commit changes only two Azure pipeline files, so `tsc7.1` and `tsrs` start from the same compiler source.

## How to run

```sh
HEAVY_LOCK=/path/to/a/lock/file sh run.sh        # everything
HEAVY_LOCK=/path/to/a/lock/file sh run.sh timing # one step
```

Steps, in order: `install`, `versions`, `snapshot`, `errors`, `accept`, `size`, `answers`, `buildinfo`, `timing`, `threads`, `faults`, `syscalls`, `vmstat`, `thp`. Every compile and every measurement runs under `flock "$HEAVY_LOCK"` (default `out/heavy.lock`), so that two heavy jobs on the same machine never overlap. The `timing`, `faults` and `thp` steps keep the lock for the whole session and wait up to five minutes for the 1-minute load average to drop under 2.0.

It needs Node.js 22.15 or newer (the TypeScript 7 and tsrs launchers call `process.execve`), Python 3 (tested with 3.14.3), git, `flock`, `unshare` and `taskset` from util-linux, `strace` (tested with 6.19), and the site dependencies installed at the repository root (`yarn install`). The recorded results used Node.js v26.12.1 and Python 3.14.3 on an Intel Core i7-1260P (4 performance cores with 2 threads each, CPUs 0-7, and 8 efficiency cores, CPUs 8-15) with Linux 6.6. Other programs were running on the laptop; every timing, fault and vmstat result records the machine state before and after its session.

The snapshot and the copy with errors are built only when they do not exist. Delete `out/subject` and `out/subject-errors` to build them again.

## What it downloads and writes

- From registry.npmjs.org, with `npm install --ignore-scripts` into `out/npm/<name>` and a private cache in `out/npm-cache`: the four packages above and their native packages `@typescript/typescript-linux-x64` (7.0.2 and 7.1.0-dev.20260930.4) and `@tsrs/linux-x64-gnu`. About 125 MB.
- `out/subject`: `git archive 703cb49` of the repository without `experiments/`, with `node_modules` as a symlink to the repository's own. In it, `contentlayer2 build` and `next typegen` run once, inside `unshare -c -n` (no network) and with `NEXT_TELEMETRY_DISABLED=1`. They write `.contentlayer/` (1,240 documents in 1,243 JSON files, and the type declarations) and `.next/types/`, as the real build does. Contentlayer also rewrites `app/tag-data.json` and writes `public/search.json`; the script restores the committed `app/tag-data.json` and moves `public/search.json` out to `out/search.json`, so the snapshot is the commit plus generated types. `.contentlayer/.cache` (about 44 MB) is not used by the compilers and can be deleted.
- `out/subject-errors`: a hard-linked copy of `out/subject` (`cp -al`). `inject-errors.py` writes each file it changes as a new file, so the clean snapshot keeps its content.
- `out/outputs`: the raw output of every compiler run. `out/buildinfo`: the build info files of the `buildinfo` check and of the incremental variants. `out/strace`: the full `strace` outputs.

## Files

| File | What it does |
| --- | --- |
| `run.sh` | runs all the steps and writes `results/` |
| `bench.py` | runs the compilers: `check` (one run each, output saved), `time` (interleaved runs with wall time, CPU time and max RSS), `threads` (samples `/proc` during one run), `buildinfo` (compares build info handling), `faults` (page faults and context switches), `syscalls` (`strace` summaries), `vmstat` (kernel memory counters around each run) |
| `thp.py` | runs a command with transparent huge pages as the system sets them, or turned off with `prctl(PR_SET_THP_DISABLE)` |
| `count.py` | groups the files of a `--listFiles` output (generated files apart from the site's own) and counts their lines |
| `compare.py` | compares `--pretty false` diagnostics between compilers: same text, same order, missing and extra errors |
| `summarize.py` | counts the error codes and the modules not found in a compiler output |
| `inject-errors.py` | puts 17 type errors into the copy of the snapshot |
| `configs/` | tsconfig variants for the snapshot (see below) |

Every run uses the command line that `next build` uses in Next.js 16.3.4 (`node_modules/next/dist/lib/typescript/runTypeCheckCli.js`): `-p <tsconfig> --noEmit --declarationMap false --emitDeclarationOnly false --tsBuildInfoFile <file>`. The `check` mode adds `--pretty false`.

## Programs that are wrong on purpose

- `configs/paths-only.json` removes `baseUrl` and adds `./` to the `paths` entries. The site imports modules like `lib/publication.mjs` and `app/seo` through `baseUrl`, so this config breaks 51 imports on purpose. `configs/migrated.json` adds the catch-all `"*": ["./*"]` mapping and is the config used for all the measurements.
- `configs/ignore-deprecations.json` adds `"ignoreDeprecations": "6.0"`, which only TypeScript 6 accepts.
- `configs/without-generated-json.json` keeps the contentlayer JSON documents out of `include`. The compilers refuse it with TS6307, because the project is `composite` and `scripts/rss.mjs` imports the generated `index.mjs`.
- `inject-errors.py` adds 17 errors to 7 files: a wrong literal for a union type, a missing JSX prop, a wrong number of arguments, two values that are possibly `undefined`, a misspelled property, a string outside a union inside an array type, a wrong argument type, a misspelled import name, a misspelled module path, a comparison that can never be true, a wrong value for a literal type, an unsatisfied generic constraint, a missing and an excess property in object literals, a forgotten `await` on the Next.js `params` promise, and a JSDoc type error in a JavaScript file with `// @ts-check`. The list is in `results/errors-made.txt`.

## Measurement method

- Each run starts without build info: `--tsBuildInfoFile /dev/null`. `results/buildinfo-check.txt` shows that a run with `/dev/null` takes as long as a run that writes a new file, and that reusing a written file makes the next run incremental (two to three times faster). The project has `incremental` and `composite` on, and tsrs and the 7.1 nightly write the same version string into their build info, so a shared file could make one compiler reuse the work of another.
- The `+incremental` variants measure the second build with nothing changed: one priming run writes `out/buildinfo/<project>-<variant>.tsbuildinfo`, then every timed run reads and rewrites it.
- `time`: one warm-up run per variant, then 11 rounds (15 for the core session). Each round runs every variant once, and the starting variant rotates from round to round. Wall time comes from `time.perf_counter_ns` around the spawn and the wait. User time, system time and max RSS come from `os.wait4` for that child, the same counters that `getrusage(RUSAGE_CHILDREN)` reports, but for one child at a time. With the TypeScript 7 and tsrs launchers, Node.js starts, then replaces itself with the native compiler through `process.execve`, so the numbers include the Node.js startup. The `-bin` variants start the native binary directly.
- The first two timing sessions run the compilers on all 16 CPUs on purpose, the way `next build` runs them, so the scheduler decides where each thread runs and the spread is part of the result. The `-pcores` and `-ecores` variants run the compiler under `taskset -c 0-7` (performance cores only) or `taskset -c 8-15` (efficiency cores only). The third timing session compares them with runs on all 16 CPUs, with 15 measured rounds.
- `timing.txt`, `timing-threads.txt` and `timing-cores.txt` record `uptime`, `free -m` and the first lines of `top` before and after each session. The `top` process lines keep only `%CPU` and `%MEM`, without user and program names. The swap of the laptop was full and about 9 GB of RAM was available during the recorded sessions.
- `threads`: one more run per variant, with `/proc/<pid>/task/*/stat` read every millisecond. Only the samples of the final program count, not the Node.js launcher before `execve`. It reports the most threads seen, the threads that used at least 20 ms of CPU, the most threads in state `R` at the same moment, the average running threads, and the share of running samples on CPUs 0-7. The sampler itself uses one CPU, so these runs are not used for timing.
- `faults`: five interleaved rounds after one warm-up run. It prints the medians of wall, user and system time, minor and major page faults, and voluntary and involuntary context switches, all from `os.wait4`, and the largest number of major page faults in any run.
- `syscalls`: `strace -f -c` on the native binaries. The call counts are reliable; the seconds that `strace` prints are not, because `strace` slows every call down. Then `strace -e trace=madvise` counts the `madvise` advice (the `MADV_HUGEPAGE` calls of tsrs come from its own memory arena), and one more run, started with huge pages turned off (`thp.py off`), records the `prctl` calls about them. In tsrs, `PR_GET_THP_DISABLE` is mimalloc's check at start, and `PR_SET_THP_DISABLE, 0` is tsrs turning huge pages back on.
- `vmstat`: reads `compact_stall`, `compact_fail`, `allocstall_movable`, `thp_fault_alloc` and `thp_fault_fallback` in `/proc/vmstat` before and after each run, in five interleaved rounds, and prints the medians of the changes. These counters are system-wide, so other programs can add to them; the TypeScript 7 rows show zero compaction stalls in the same minutes. The file also records the transparent huge page settings of the laptop (`enabled` is `always`, `defrag` is `madvise`).
- `thp`: 11 interleaved rounds with transparent huge pages as the system sets them (`-thp-default`) and turned off (`-thp-off`). For TypeScript 7, `thp.py off` sets `PR_SET_THP_DISABLE`, which stays after `execve`. For tsrs this does not work. tsrs builds mimalloc 3.5.2 (see `versions.txt`) with `allow_thp = 0`, so mimalloc turns huge pages off for the whole process at start ([`src/prim/unix/prim.c`, lines 265-276](https://github.com/microsoft/mimalloc/blob/v3.5.2/src/prim/unix/prim.c#L265-L276)), and then tsrs's `init_mimalloc` turns them back on for its arena, unless `MIMALLOC_ALLOW_THP` is set ([`crates/tsrs_core/src/allocator.rs`, lines 3-17, v0.18.0](https://github.com/oxc-project/tsrs/blob/v0.18.0/crates/tsrs_core/src/allocator.rs#L3-L17)). So the tsrs variants use `MIMALLOC_ALLOW_THP=0`. The tsrs authors measured that with huge pages off for the whole process, tsrs was 3% to 25% slower on 32-vCPU servers with THP in `madvise` mode ([`notes/mem-no-thp.md`, lines 190-197, v0.18.0](https://github.com/oxc-project/tsrs/blob/v0.18.0/notes/mem-no-thp.md?plain=1#L190-L197)). The 30% gain measured here comes from the state of this laptop (full swap, failed compactions, `defrag` set to `madvise`), not from a general rule. Each pair runs through the same wrapper (`thp.py` or `env`), with and without the change.
- The results print paths relative to this directory. `node_modules/...` stands for the repository's `node_modules`, and `DIR` for the home directory.

## Results

| File | Content |
| --- | --- |
| `versions.txt` | machine, Node.js, Python, compiler versions, package and binary sizes |
| `accept.txt` | the five configs on the four compilers (for `paths-only`, the error counts, the modules not found and the first two lines, not the full list) |
| `files.txt` | the files the compilers read, grouped (generated files apart), and the differences between the file lists |
| `extended-diagnostics.txt` | `--extendedDiagnostics` of each compiler on the migrated config |
| `errors-made.txt` | the 17 deliberate errors |
| `diagnostics-<compiler>.txt` | the diagnostics of each compiler on the copy with errors |
| `diagnostics-compare.txt` | the comparisons, thread settings, five repeated runs and exit codes |
| `buildinfo-check.txt` | new build info file, the same file again, and `/dev/null` |
| `timing.txt` | the four compilers, launchers against native binaries, and incremental runs |
| `timing-threads.txt` | the thread settings of TypeScript 7.0 and tsrs |
| `timing-cores.txt` | tsc 6, TypeScript 7.0 and tsrs on all CPUs, on the performance cores only and (except tsc 6) on the efficiency cores only |
| `threads.txt` | thread counts and core types during one run of each |
| `faults.txt` | page faults and context switches of TypeScript 7.0 and tsrs, with and without threads |
| `syscalls.txt` | `strace` summaries, `madvise` counts and the `prctl` calls about huge pages of both native compilers |
| `vmstat.txt` | huge page settings and kernel memory counters around each run, with huge pages on and off |
| `timing-thp.txt` | TypeScript 7.0 and tsrs with huge pages as the system sets them and turned off |

Timing numbers change from run to run and from machine to machine. The answers, the file counts and the accept results should not.
