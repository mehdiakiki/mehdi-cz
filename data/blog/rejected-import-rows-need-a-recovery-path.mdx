The import finishes with a warning: twelve rows failed. The job is marked complete, and the only explanation is a few lines in yesterday's logs.

Which rows? Can they be corrected? Will retrying the file duplicate the rows that succeeded?

An importer needs answers to those questions before it is useful for real data. A rejected row is an outcome the system must manage, not an exception to discard so the job can turn green.

## Decide whether rows succeed together

A bulk operation can be atomic, or it can accept independent rows. State the contract before designing the status page.

For an atomic batch, one invalid row may roll back every row in that batch. Do not label the other rows committed because the client successfully sent them. For independent outcomes, preserve a stable identity for every item and report which ones actually committed.

The [SQL Server bulk-loading example](/blog/loading-a-batch-into-sql-server-from-rust) distinguishes sending rows, finishing the bulk stream, and completing the surrounding transaction. Tiberius's [bulk request documentation](https://docs.rs/tiberius/latest/tiberius/struct.BulkLoadRequest.html) describes finalization. Application-level progress must follow the boundary your importer promises.

## Keep a small rejection record

A rejection needs enough information for a human or a repair process to find the original input and understand the decision. Here is a Rust model for that record:

```rust
struct RejectedRow {
    import_id: String,
    source_record_id: String,
    source_version: String,
    reason_code: String,
    parser_version: String,
    status: RepairStatus,
}

enum RepairStatus {
    Waiting,
    Resolved,
    Discarded { reason: String },
}
```

This is a data model, not a complete storage implementation. Give identities, reason codes, and explanatory text size limits. Keep private source payloads in an appropriately protected store if they must be retained; copying full rows into ordinary logs creates another data problem.

Store row numbers only as a convenience. They are fragile when a file changes or a provider returns a different order. Use the source's stable identity and an input version or content identity where possible.

## Repair should be repeatable

Correct the input or mapping, then replay a selected rejection under the original import identity and a recorded correction version. The handler needs a duplicate policy for a row that already succeeded during an earlier attempt.

Keep the original rejection history when marking it resolved. Otherwise the next engineer cannot tell whether data was fixed, silently dropped, or accepted under a different rule.

If a row is intentionally discarded, make that a separate, explained outcome. Some source data is genuinely unusable. Hiding that decision inside a catch block makes the import totals misleading.

## Check the counts against stored data

Build a small fixture with valid rows, a malformed value, a constraint violation, and a duplicate identity. Interrupt the job after some committed work, then resume it.

Assert the committed rows and rejection records, not just the final summary. Correct one rejected row and replay it twice. It should produce the intended stored result without an extra business effect.

Run this recovery check against SQL Server with the actual constraints and transaction settings. Parser tests cannot show whether the bulk operation committed or rolled back. The importer becomes easier to trust when “complete” means every input has a known outcome.
