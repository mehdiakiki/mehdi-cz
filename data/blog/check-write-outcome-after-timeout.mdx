The provider creates the order. Its response gets lost. Your client times out and submits a new request with a new key.

There are now two orders, although the code was only trying to recover from a failure.

A timeout tells the client that it did not get a result within its limit. It does not always tell the client whether the remote write happened.

## Keep an unresolved state

Model what the client actually knows. This Rust enum is a small example:

```rust
enum WriteOutcome {
    Confirmed { remote_id: String },
    Rejected { reason_code: String },
    Unresolved { operation_id: String },
}
```

Unresolved is useful information. It prevents the application from claiming a definite failure while it is still possible that the provider accepted the operation.

Create the stable operation identity before sending the write and persist it when the workflow must survive a restart. Bind it to the relevant payload so the same identity cannot quietly mean a different order later.

The [idempotency-key guide](/blog/idempotency-key) explains the server-side contract. A client must use the particular provider's guarantees, including retention windows, payload conflict handling, and which operations support deduplication.

## Recover using evidence the provider supports

Some providers offer lookup by request identity. Some document that retrying the same key returns the earlier result. Others expose a separate asynchronous operation status.

Use the supported path. Keep the original identity and payload. A new random key starts another logical operation even if the code calls it retry.

A lookup that finds nothing may still be inconclusive if writes become visible asynchronously. Read the documented consistency and retention contract before treating absence as proof that nothing happened.

If the provider has no reliable lookup or duplicate protection, keep the uncertain state visible and give an operator a way to resolve it. The client cannot create a guarantee the provider does not offer.

HTTP's [retry discussion](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) is a useful starting point, but an application-specific write needs its own semantics.

## Tell the caller what to do next

An API can return an operation identity and expose a status lookup. The interface can show that confirmation is pending rather than inviting a second purchase immediately.

Do not make the user carry the entire recovery burden with “please try again” if that action can duplicate a write. Decide how repeated submissions relate to the same intent.

Keep local expiry separate from remote outcome. Giving up on automatic recovery does not reverse a remote order. A manual resolution can still be required after the client's retry budget ends.

## Simulate a committed write with no response

Build a controlled provider that records the order and then closes the connection before returning its result. The client should enter the unresolved path and recover the same order identity.

Also test a rejection before acceptance and a provider that remains unavailable during lookup. Assert the number of stored orders, not just the client's final message.

This is a small failure to reproduce and a costly one to miss. Once the client distinguishes “no response” from “no write,” the retry policy becomes much easier to reason about.
