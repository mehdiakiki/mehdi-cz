The client completes more requests per second after its concurrency limit is raised. The graph looks better. Users report that some requests now take much longer.

Both observations can be true. A throughput improvement can come with longer queues and worse latency for the slow end of the workload.

Before increasing the limit again, I would measure what happens to those requests, including the time they spend waiting to start.

## Keep the workload comparable

Use the same request mix, payload sizes, upstream behaviour, and measurement window. Record errors and timeouts rather than excluding them from the latency report.

Decide whether the workload sends requests at an independent arrival rate or waits for completion before sending more. A closed-loop client can reduce offered work when responses slow down. That can hide the queue a real traffic burst would create.

Neither workload model is always wrong. State which one matches the question being asked and what it cannot show.

The [adaptive-concurrency article](/blog/adaptive-concurrency-for-apis-with-changing-rate-limits) discusses limits when upstream capacity changes. This experiment should first establish how the fixed limits behave for one controlled workload.

## Start timing before the local queue

In a Rust client, record admission wait separately from the actual upstream operation. This is an instrumentation outline:

```rust
let queued_at = std::time::Instant::now();
let permit = limiter.acquire().await?;
let started_at = std::time::Instant::now();
let result = transport.send_and_read_bounded(request).await;
let finished_at = std::time::Instant::now();
drop(permit);

record_queue_wait(started_at.duration_since(queued_at));
record_upstream_time(finished_at.duration_since(started_at));
record_total_time(finished_at.duration_since(queued_at));
```

The helpers are application-specific. Here, `send_and_read_bounded` finishes only after reading the required response body within its size limit. Clients such as reqwest expose [body reads separately from response headers](https://docs.rs/reqwest/latest/reqwest/struct.Response.html). Stopping the timer when headers arrive can miss a slow body and release the concurrency permit too early.

A production implementation also needs cancellation and deadline accounting so timed-out requests remain visible in the outcome data. Include the body-reading policy in the workload description.

Report a distribution and sample count. A high percentile from a tiny sample can look more precise than the evidence supports. Keep raw or suitably aggregated observations available for review without exposing private request data.

## Look for the first resource that saturates

The limit may protect a provider quota, a connection pool, CPU, or memory. Increasing it can move waiting to another layer instead of creating useful capacity.

Watch active requests, local queue wait, upstream latency, rejection rate, and timeouts together. If throughput barely changes while queue time grows, more in-flight work may mainly be adding delay.

Tokio's [semaphore documentation](https://docs.rs/tokio/1.48.0/tokio/sync/struct.Semaphore.html) explains the local permit mechanism. Its configured count is the limit you chose. It does not measure what the upstream can currently handle.

## Pick the limit for the product

A background backfill may accept slower individual requests to maximize completion rate. An interactive search endpoint may prefer early rejection or a smaller queue to keep response time bounded.

Test several limits through the existing CI or performance workflow. Include an unchanged control and repeat when shared-runner variation matters. Publish measured figures only with the workload and environment that produced them.

The useful conclusion is not “more concurrency is bad.” It is a specific limit, for a specific workload, chosen using both completion rate and the experience of slower requests. Average speed alone cannot make that decision.
