One of the hardest operational questions is also very small: “What happened to this record?”

The temptation is to log the whole payload at every stage. Then searching is easy—until the logs contain names, tokens, addresses, documents, and data that should have been deleted months ago.

I want another kind of observability. I want to follow the record's journey while keeping its contents in the system that is allowed to hold them.

## One identifier cannot explain every relationship

I separate at least four identities:

```text
trace_id          one execution path through services
record_id         the stable business/canonical entity
event_id          one immutable observation or message
causation_id      the event or command that caused this one
```

A retry may create a new trace for the same event. One event may update several records. A replay may process the same record under a new replay identity. Trying to force all of these into `correlation_id` makes queries ambiguous.

The [W3C Trace Context specification](https://www.w3.org/TR/trace-context/) standardizes trace and parent identifiers across service boundaries. I use that for execution causality. I keep business and event identities as explicit application attributes.

## The record reference must be safe to index

If an email address is the provider's identity, I do not put the email into every log line. I first map it to an internal opaque identifier.

When that is impossible, a keyed fingerprint can support correlation:

```text
record_fingerprint = HMAC(rotation_key, tenant_namespace || external_id)
```

I use HMAC, not a plain hash, because low-entropy identifiers can be guessed. The tenant namespace prevents accidental cross-tenant correlation. The key version is recorded so fingerprints can rotate.

This is still potentially sensitive metadata. Access control and retention apply. “Hashed” does not mean anonymous.

## My stage event is deliberately boring

Each important boundary emits a structured event:

```json
{
  "trace_id": "4bf9...",
  "record_ref": "account/a-19",
  "event_id": "evt_884",
  "causation_id": "evt_881",
  "stage": "normalize.account",
  "attempt": 2,
  "input_version": "provider-v4",
  "mapping_version": "account-v7",
  "outcome": "QUARANTINED",
  "reason": "UNKNOWN_LIFECYCLE_VALUE",
  "observed_at": "2026-12-17T08:14:00Z"
}
```

It does not contain the unknown value if that value may be sensitive. A controlled evidence store can retain the source payload under stricter access, and the event points to its evidence identity.

The version fields often solve the incident faster than the payload. They tell me which contract and mapping made the decision.

## Trace context and message lineage both matter

HTTP calls form a parent-child trace naturally. Queues and batch jobs do not always fit one long-lived parent tree.

For an asynchronous message I propagate trace context when it represents one causal continuation. For a batch combining many messages, I use trace links rather than inventing one parent. OpenTelemetry's [context propagation documentation](https://opentelemetry.io/docs/concepts/context-propagation/) describes how context crosses process boundaries.

I also store event lineage in durable data. Traces are sampled and expire; business causation may need to survive much longer.

```text
source event evt_881
  -> normalized event evt_884
  -> projection update op_220
  -> repair case repair_31c
```

This chain remains queryable even if no single trace contains the complete lifecycle.

## Baggage is not a secret transport

OpenTelemetry baggage can propagate application values through a distributed request. It is convenient and easy to misuse. Baggage may reach downstream processors and exporters, so I do not place raw customer identifiers, prompts, access tokens, or document text in it.

I propagate opaque references and low-cardinality policy versions. High-cardinality record identity may belong on spans or structured events with controlled indexing rather than general metrics labels.

Metrics such as `pipeline_records_total{email=...}` would be both a privacy problem and a cardinality problem.

## The query follows a timeline

My operational view starts from a safe `record_ref` and returns:

| Time | Stage | Version | Outcome | Link |
| --- | --- | --- | --- | --- |
| 08:13:58 | ingest | provider-v4 | accepted | trace A |
| 08:14:00 | normalize | mapping-v7 | quarantined | evidence E |
| 09:02:11 | repair | mapping-v8 | applied | trace B |
| 09:02:13 | verify | canonical-v81 | converged | repair R |

The operator can see the story without opening payload content. If deeper access is justified, evidence retrieval is a separate audited action.

This connects with [record-level provenance](/blog/record-level-provenance-explain-where-a-normalized-field-came-from): tracing explains processing, while provenance explains which source observation produced a field value.

## Sampling cannot erase every failure

Head sampling may discard a trace before a later failure becomes known. For high-value pipelines I keep lightweight structured stage events for every terminal outcome and use tail sampling or forced retention for errors.

I do not sample away:

- quarantines and invariant failures;
- ambiguous external outcomes;
- authorization denials indicating possible policy bugs;
- replay and repair activity;
- version mismatches;
- unexpectedly old freshness.

Successful high-volume paths can be sampled more aggressively, provided aggregate counts still reconcile.

## Deletion must reach observability data

Logs and traces are separate stores with separate retention. If a product deletion obligation applies to record-linked operational data, I need an index that can locate it by the safe reference or key version.

Sometimes the correct policy is short immutable retention rather than per-record deletion. Sometimes regulated evidence must remain longer. I document the decision by data class; observability is not automatically exempt from product privacy rules.

## Tests I run

I send one synthetic record through success, retry, quarantine, replay, repair, and deletion paths. Then I verify:

1. Every stage can be joined by documented identities.
2. A retry keeps logical event identity but has a distinct attempt.
3. A replay carries both source and replay identities.
4. No forbidden field appears in logs, traces, baggage, or metric labels.
5. Unknown values are diagnosable through controlled evidence.
6. Key rotation preserves the promised query window.
7. Expired observability data actually disappears.

I include an automated secret canary in the fixture and fail the test if it reaches an exporter.

The result I want is not “we log everything”. It is stronger: I can reconstruct why one record moved, stopped, or changed using stable identity, lineage, versions, and reason codes—and I can do it without turning the observability system into an uncontrolled copy of production data.
