An AI prototype often has one path: call the model and show the result. The first fallback is usually an exception handler that says “please try again”.

That may be acceptable for a novelty. It is weak when the feature sits inside somebody's real work.

I prefer to design the non-AI path while the normal path is still being designed. It forces me to answer what the product actually does for the user, independently of how intelligent the model looks.

## “Unavailable” has several meanings

The provider can be down, but many other conditions should enter the fallback path:

```text
provider timeout or outage
rate limit or exhausted task budget
model output fails validation
retrieval has no authorized evidence
safety policy blocks the operation
confidence or evaluation gate is too low
user or tenant disables AI processing
required region/model is unavailable
```

Treating all of these as HTTP 500 loses the product decision. A safety block should not retry like a network timeout. Missing evidence should not fall back to a cheaper hallucination.

## I classify the feature by consequence

The fallback depends on what AI is doing.

| AI role | Example | Useful non-AI path |
| --- | --- | --- |
| convenience | rewrite or summarize | original content remains available |
| discovery | semantic search | keyword/filter search |
| recommendation | ranked next action | deterministic list or no recommendation |
| extraction | fill structured fields | manual form with source beside it |
| decision support | flag risk | queue for human review |
| action agent | modify external system | stop safely; preserve draft and evidence |

For irreversible actions, “use a smaller model” is not automatically graceful degradation. The safe fallback may be no action.

## The state machine is visible to the user

I model the feature explicitly:

```text
AVAILABLE
DEGRADED_NON_AI
QUEUED_FOR_LATER
NEEDS_HUMAN_REVIEW
UNAVAILABLE
```

The interface says which state it is in. It does not show an old cached answer as new, silently omit half the workflow, or call a deterministic fallback “AI-generated”.

For a document assistant, this could mean:

```text
available: answer with verified citations
degraded: keyword results with highlighted passages
queued: analysis will run later, document remains usable
review: extracted fields shown as unresolved
unavailable: editing and export still work
```

The product keeps a useful core instead of becoming a loading spinner around a provider.

## Build the ordinary software path seriously

I do not see a non-AI path as embarrassing legacy code. It uses normal engineering strengths: indexes, rules, type-safe validation, transactions, state machines, and clear user interaction.

Keyword retrieval can be excellent for identifiers and exact terminology. A manual form can be faster than correcting a weak extraction. Deterministic templates can produce consistent regulated output. A queue can preserve work until capacity returns.

AI is one component in this design. Knowing where not to use it is part of building a strong AI product.

## Fallback data must obey the same permissions

A common mistake is securing the AI retrieval path but letting fallback search query a broader store. Every state uses the authenticated user's current authorization.

Cached or last-known results need freshness and permission checks. My article on [caching AI results](/blog/caching-ai-results-requires-an-identity-and-freshness-model) explains why “we computed it earlier” is not sufficient authorization now.

If a non-AI fallback cannot maintain the same policy, it is not available for that request.

## Circuit breakers protect recovery

When a provider is failing, immediate retry from every request can keep it failing and consume our capacity.

I use bounded retries for individual calls and a circuit state for the shared dependency:

```text
CLOSED     normal calls
OPEN       fail fast into product fallback
HALF_OPEN  limited probes test recovery
```

The product state derives from more than provider health. Budget, queue age, model policy, and safety gates can open their own degradation conditions.

I add jitter and admission control when service returns. Sending the entire queued backlog at once is not recovery.

## Queued work needs an expiry and identity

“We will process it later” is a promise. I record:

```text
task identity
input and authorization snapshot policy
requested outcome
created and expiry time
current status
cancellation control
notification preference
```

Before delayed execution I re-check permissions and freshness. A user may have deleted the source or lost access while the task waited.

If the answer is no longer useful after ten minutes, I expire it rather than producing expensive stale work three hours later.

## Tests begin by turning the model off

I run scenarios where the model client never succeeds:

1. Timeout before any output.
2. Failure after partial streamed output.
3. Rate limit for one tenant and globally.
4. Invalid structured output repeatedly.
5. Retrieval returns no permitted source.
6. Budget is exhausted before fan-out.
7. Provider recovers while backlog exists.
8. User cancels queued work.

For each case I verify the visible state, retained work, side effects, metrics, and recovery path.

The [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework) emphasizes managing AI risk across design, deployment, and operation. For me, a tested non-AI path is one concrete way to reduce dependence on a component whose availability and output are not fully under my control.

## Metrics should show product degradation

Provider uptime is not enough. I measure:

- requests served through each product state;
- completion and abandonment in the fallback path;
- queued work age and expiry;
- human-review load;
- quality difference between normal and degraded paths;
- cost avoided and useful work lost;
- time from dependency recovery to product recovery.

If users cannot complete the job through the fallback, I call it unavailable rather than celebrating a technically successful HTTP response.

## The question I use in design review

I ask: if every model call returns an error for the next four hours, what can the user still accomplish safely?

The answer exposes whether AI enhances a product or has become the product's only structural support. Sometimes an AI-only feature is a valid choice. Then the honest fallback is a clear unavailable state, saved input, and no accidental effects.

Most of the time, though, there is a useful ordinary path. Designing it keeps the system practical during outages and keeps my own engineering honest: I use AI where it adds value, while the surrounding product still rests on explicit software contracts.
