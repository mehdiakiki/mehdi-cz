When a new system needs many integrations, workflows, or data types, the efficient-looking approach is to build the framework first.

We design a universal connector interface, a generic scheduler, a mapping language, and a plugin registry. Then the first real use case arrives and does not fit.

The framework was consistent. Reality was more specific.

The principle I prefer is:

> Build one narrow but complete path through the system before generalizing its layers.

This is a vertical slice. It gives architecture real pressure to respond to.

## Horizontal progress can hide missing decisions

A horizontal plan builds each layer separately:

```text
week 1: connector framework
week 2: storage framework
week 3: mapping framework
week 4: execution framework
week 5: connect everything
```

Each piece can look nearly finished while no user outcome works.

The integration week then reveals disagreements:

- the connector cannot express deletion;
- storage identity does not match source identity;
- the mapper needs provenance that was discarded;
- execution needs freshness but only import time was stored;
- retrying a page creates duplicates;
- permissions were attached after data crossed the boundary.

These are not wiring mistakes. They are missing product contracts.

## A slice follows one real outcome

For a data integration, a narrow slice could be:

```text
authenticate one source
      ↓
fetch one resource type with real pagination
      ↓
preserve source identity
      ↓
map it into one product concept
      ↓
validate and store it
      ↓
use it in one product behaviour
      ↓
observe and retry the path
```

This is small in breadth and complete in depth.

It should use real constraints. Fake data that never paginates and a provider that never returns an error teach very little about an integration architecture.

The slice does not need every production optimization. It does need to cross the boundaries whose shape we are trying to learn.

## Choose the slice for information, not convenience

The easiest use case is not always the best first slice. A useful slice contains one or two representative difficulties without containing all of them.

Good selection questions are:

- Does this source use the normal authentication model?
- Does it include pagination or incremental change?
- Is the resource meaningful to an actual product workflow?
- Will it exercise identity and mapping?
- Can we run it safely with a small scope?
- Will success or failure teach us about the common path?

Avoid the strangest provider first. It can force every abstraction to serve an exception. Also avoid a toy provider that proves only that HTTP and JSON work.

## Keep the first implementation honest

"We will clean it later" can turn a slice into disposable code. A learning slice is more valuable when it is production-shaped:

- secrets are not hard-coded;
- failures are typed or classified;
- important steps have structured logs;
- writes can be repeated safely;
- checkpoints have clear meaning;
- test fixtures contain realistic variants;
- operator-visible status distinguishes progress from activity.

This does not mean building a full platform. It means learning from the same constraints the real system will face.

## Do not call the first shape generic

After one implementation, we know one implementation.

Suppose the first provider uses page numbers:

```ts
type Connector = {
  nextPage(page: number): Promise<Page>;
};
```

The second provider uses opaque cursors. The third offers a change stream. `page: number` was not a universal connector concept. It was one provider's mechanism.

A better early boundary can express intent:

```ts
type Checkpoint = unknown;

interface SourceReader {
  readAfter(checkpoint?: Checkpoint): Promise<Batch>;
}
```

Even this may change. The point is to name the operation we need, while keeping provider mechanics inside the provider.

The [stable internal model article](/blog/stable-internal-model-api-integrations) applies the same idea to data shape.

## Generalize from differences, not similarities alone

Two connectors both make HTTP requests and parse JSON. This similarity is too low-level to define a useful product abstraction.

More important comparisons are:

- What is a stable resource identity?
- How is progress resumed?
- How are updates and deletion represented?
- Which failures block the whole source?
- What freshness can the source provide?
- Which source facts must remain available after mapping?

Write these differences down after each slice. A good shared interface emerges from repeated obligations. Provider-specific policy stays in adapters.

Sometimes two cases show that no shared abstraction is needed yet. A little duplication can be cheaper than the wrong shared contract.

## Use the second slice to attack the design

The second implementation should not only prove reuse. It should challenge the first boundary.

Choose a case with a meaningful difference:

- cursor pagination after page-number pagination;
- webhooks after polling;
- mutable records after immutable events;
- organization-scoped credentials after user-scoped credentials;
- hard deletion after sources that only update.

When the design changes, inspect which parts move:

- If only the adapter changes, the boundary may be healthy.
- If the canonical model changes, we may have found a missing product concept.
- If every consumer changes, provider details probably leaked too far.
- If the framework gains many flags, two different abstractions may be hiding under one name.

This is architecture as a testable hypothesis.

## A complete slice improves planning

Once one path works, estimates for the next path become less fictional. We know the work categories:

- provider-specific access;
- mapping and validation;
- identity and lifecycle;
- recovery and reconciliation;
- operations and support;
- product integration.

We also know where product decisions are required. This matters in early teams because an unknown product rule can block engineering more than an unknown library.

The slice gives founders and engineers the same concrete object to discuss.

## What I learned from building systems from the beginning

Building foundational systems taught me that end-to-end ownership produces a different kind of information. A component can be locally clean and still make the whole path unsafe. Seeing one record move from an outside boundary into real product behaviour exposes these gaps early.

The example here is generic and intentionally not tied to one company or implementation. The lesson is that architecture becomes stronger when it is corrected by a complete working path.

## A vertical-slice checklist

Before building a general framework, ask:

- What is the smallest real user outcome that crosses the whole system?
- Which difficult boundary must it include?
- Are we using realistic source behaviour and failures?
- Can the path restart without guessing?
- Does it reach product behaviour, not only storage?
- Which assumptions did the first implementation create?
- How will the second slice challenge those assumptions?
- Is duplication currently cheaper than a false abstraction?

Build enough of the whole to understand the parts. Then generalize what reality has repeated.
