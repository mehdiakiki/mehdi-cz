At the beginning of a product, architecture diagrams can look unusually clean. This is partly because the system is small. It is also because many facts are still missing.

We do not yet know which workflow customers will use most, which integration will be difficult, which data must be retained, or where scale will appear first.

The first architecture is therefore built with incomplete information. Its job is not to predict every future requirement.

The principle I use is:

> Early architecture should make important decisions explicit and uncertain decisions inexpensive to change.

## Good early architecture buys learning

Architecture has a cost. A new service, queue, plugin system, or generic workflow engine takes time to build and creates an interface we must maintain.

The return should be more than visual elegance. An early technical decision should do at least one of these things:

- remove a serious product risk;
- let us test a real workflow;
- protect data or security boundaries;
- make failure visible;
- teach us what the next design needs.

If it does none of them, it may be architecture for an imagined company.

A narrow end-to-end feature can produce more useful information than a broad framework. It shows where real data is irregular, where latency matters, and which concepts customers actually need.

## Separate hard-to-reverse from easy-to-reverse decisions

Not every decision deserves the same ceremony.

Harder decisions often include:

- public API contracts;
- persistent identifiers;
- ownership of source data;
- security and permission boundaries;
- irreversible migrations;
- promises made to customers.

Easier decisions often include:

- an internal library;
- a replaceable storage adapter;
- a queue implementation behind one interface;
- how an internal page is organized;
- a deployment detail with a tested rollback.

This classification is contextual. Changing a database can be easy for an empty prototype and very hard after three years of customer data.

The useful habit is to ask about reversibility before adding process. Spend design time where reversal is expensive.

## Keep stable boundaries small

A boundary becomes costly when many parts of the product depend on it. Early boundaries should therefore expose the smallest contract that is already supported by evidence.

For an integration system, this might be:

```ts
type SourceRecord = {
  source: string;
  resourceType: string;
  externalId: string;
  observedAt: string;
  payload: unknown;
};
```

This contract says little about how providers authenticate, paginate, or schedule work. Those details can remain inside adapters until several implementations show what is truly shared.

Small contracts are easier to preserve. Large early abstractions often include guesses that later become obligations.

## Delay generality, not quality

"We can change it later" is sometimes used to excuse unsafe work. That is not the goal.

Even a first version should have:

- explicit error handling;
- basic observability;
- clear ownership of state;
- tests for its important contract;
- a rollback or recovery path;
- safe treatment of credentials and personal data.

What can wait is speculative generality: ten extension points for one known use case, a distributed deployment for no measured load, or a configuration language before the product behaviour is stable.

Quality makes change safer. Premature generality makes change harder.

## Prefer replaceable implementations over fake universality

A useful early design can have one real implementation behind a narrow port:

```ts
interface RecordSink {
  apply(records: SourceRecord[], checkpoint: string): Promise<void>;
}
```

This does not require building several sinks to prove the interface is generic. It only prevents the first sink's database client from leaking through every caller.

There is also a danger here. Interfaces created only for testing can mirror one implementation so closely that they add indirection without options. The boundary should express a product operation, not every method of a vendor SDK.

## Record assumptions beside decisions

An architecture decision without its assumptions becomes difficult to revisit.

Instead of writing:

> We will process all providers through one worker pool.

Write:

> We expect provider work to be independent, below this concurrency range, and safe to retry. One worker pool is the smallest design that tests these assumptions. Revisit if isolation or scheduling policies diverge.

Now the decision has a trigger for change.

A short decision record can include:

- context;
- decision;
- alternatives considered;
- current assumptions;
- consequences;
- evidence that should make us revisit it.

This is more valuable than pretending the decision is permanent.

## Design the migration seam before the replacement

When one component is likely to change, we do not need to build its future replacement. We need a clean place to replace it.

Examples:

- keep persistence calls inside one repository module;
- translate third-party payloads at one boundary;
- keep authorization in a server-side policy layer;
- use stable identifiers rather than database row positions;
- make background work restartable;
- version durable messages.

These seams are small investments. They reduce the blast radius if the assumption changes.

## Know when to harden

The first architecture should evolve when evidence arrives. Useful triggers include:

- a second implementation exposes duplicated behaviour;
- one workload needs independent scaling or failure isolation;
- deployments are blocked by unrelated components;
- recovery time is outside the product requirement;
- data volume breaks a measured limit;
- permissions require a stronger boundary;
- several teams need to change the same module independently.

"We may need it someday" is weak evidence. Repeated operational pain is strong evidence.

The change can still be proactive. We do not need to wait for an outage. Measurements, customer commitments, and credible growth can show that a limit is approaching.

## What I learned from foundational product work

Working on products while their architecture was still taking shape changed how I see the first version. The difficult part was not choosing fashionable components. It was deciding which boundaries needed to be dependable before all requirements were known.

The examples here are generic. The durable lesson is that an early system needs both discipline and humility: discipline around the contracts that matter, and humility about the assumptions that have not met reality yet.

## A first-architecture checklist

Before making an early design expensive, ask:

- Which real risk does this decision remove?
- What will we learn by shipping it?
- Is the decision hard to reverse?
- Which contract must remain stable?
- Which detail can stay behind a small boundary?
- Are we delaying generality or delaying basic quality?
- What evidence will tell us to revisit the design?
- Can we recover when the first assumption is wrong?

The best first architecture is not the one that looks final. It is the one that lets the product become less uncertain without making every discovery painful.
