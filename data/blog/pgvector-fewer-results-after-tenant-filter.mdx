Your retrieval tool asks PostgreSQL for five documents. It returns fewer than
five, although the customer owns enough documents. An AI answer built from that
result may sound incomplete. Changing the prompt cannot recover rows that never
reached the model.

Start below the answer generation. Confirm that enough eligible rows exist, then
compare the approximate search with an exact search over the same eligible data.
That comparison gives you a way to investigate a proposed fix without guessing
whether the model needs a longer context or different embeddings.

This article uses a small Rust fixture with SQLx 0.8.6, PostgreSQL 18 and pgvector
0.8.7. HNSW is pgvector's graph-based approximate nearest-neighbor index. It trades
an exhaustive distance calculation for a search through candidate neighbors.
We use three-dimensional synthetic vectors so that the intended nearest eligible
rows are easy to identify. There is no embedding model or language-model call in
this experiment.

## Establish which five rows should be available

The fixture creates 1,024 documents. The first 1,000 belong to beta. The final 24
belong to alpha. Each vector's first coordinate increases with its ID, and the
query vector is the origin. This deliberately puts many beta neighbors ahead of
the nearest alpha document.

Only alpha is eligible for this request. The exact reference applies that tenant
predicate and calculates the nearest five alpha vectors. Its intended IDs are
1,001 through 1,005. The distances are distinct, so an arbitrary tie order cannot
explain a different result.

The reference is also an authorization rule. Comparing the filtered query with
an unrestricted top five would measure the wrong task. A result from another
tenant is not a useful substitute for a missing authorized result, however close
its vector may be.

For this fixture, the exact path disables index and bitmap scans in its own
transaction. That is a diagnostic control, not a recommendation to change server
defaults. In an application, inspect the actual plan to confirm that the chosen
reference is exhaustive for the distance operation and snapshot you are using.

If the exact path also returns fewer than five, first inspect the eligible row
count, visibility rules, deleted documents and query predicates. An approximate
index is not needed to explain every short result set.

## Check the execution plan before explaining the result

Next, the fixture enables index scans, discourages a sequential scan, disables
iterative search, and sets a small candidate-search setting. It saves an
`EXPLAIN ANALYZE` plan and requires the expected HNSW index scan to appear.

That plan check matters. A query written for vector search can still use another
path. Without observing the path, a passing test could compare two exact scans
while claiming to test approximate search.

The [pgvector 0.8.7 filtering documentation](https://github.com/pgvector/pgvector/blob/v0.8.7/README.md#filtering)
explains that an approximate index scan can produce candidates which the filter
then removes. Here beta occupies the near neighborhood. A limited search can
finish with too few surviving alpha rows. `LIMIT 5` caps the output; it does not
make an approximate search inspect enough eligible candidates.

Do not repair this by retrieving another tenant's text and asking the model to
ignore it. Eligibility belongs in the database operation and its authorization
contract. Keep the predicate while investigating how much search work is needed.

## Change the search work while keeping the question fixed

One candidate is an iterative HNSW scan. The fixture enables strict ordering and
keeps an explicit scan-work setting:

```rust
sqlx::raw_sql(
    "SET LOCAL hnsw.iterative_scan = strict_order;
             SET LOCAL hnsw.max_scan_tuples = 20000",
)
.execute(&mut *tx)
.await?;
let recovered: Vec<i32> = sqlx::query_scalar(
    "SELECT id FROM documents WHERE tenant_id = $1
             ORDER BY embedding <-> '[0,0,0]'::vector LIMIT 5",
)
.bind("alpha")
.fetch_all(&mut *tx)
.await?;
```

The surrounding code creates the data and index, records the plan, and compares
this result with the reference. It lives in
[the complete Rust fixture](https://github.com/mehdiakiki/mehdi-cz/blob/editorial/ai-era-sql-2026-10-31/experiments/rust-backend/tests/ai_database_review.rs).

The assertions require a short result from the limited approximate path, followed
by the same five IDs as the exact reference after changing the search behavior.
All returned IDs must remain in alpha. This gives the repair a concrete target
and checks that it did not improve apparent recall by widening access.

The value 20,000 belongs to this controlled dataset. It is not a proven capacity
limit or a production recommendation. Iterative scans still have stopping
conditions. Strict ordering orders the results found by the search; it does not
promise that every approximate query finds the global exact top five.

## Compare repairs against the same reference

An AI assistant can suggest several reasonable changes. Keep the query, eligible
corpus and reference fixed while evaluating each proposal:

| Candidate                                  | Evidence to request                                                 | Cost or limitation to inspect                        |
| ------------------------------------------ | ------------------------------------------------------------------- | ---------------------------------------------------- |
| Search more candidates                     | Eligible count and recall improve against the exact reference       | More database work and longer waits under load       |
| Use exact search after a selective filter  | Plan visits the eligible subset and returns the reference neighbors | Cost grows with the size of that subset              |
| Separate some tenant indexes or partitions | Target tenants improve without changing access rules                | Extra index storage, routing and maintenance         |
| Change the embedding model                 | A labeled relevance set improves on meaningful queries              | Re-embedding cost, migration work and a new baseline |

The synthetic fixture establishes a mechanical counterexample. It does not tell
you whether two real documents mean the same thing. Distance recall and useful
retrieval are related but different measurements. Compare semantic relevance
with labeled queries as a separate evaluation.

For a top-k reference, divide the number of returned reference IDs by the smaller
of k and the number of eligible rows. Track returned-row count separately. Five
rows can still be the wrong five. Keep ties, data freshness and simultaneous
updates consistent when comparing runs; this fixture uses one transaction and
distinct distances to remove those ambiguities.

Also check several tenant sizes. A global average can hide a small tenant that
rarely gets enough results. An embedding migration can change the candidate
distribution even when the application query stays unchanged. Preserve the
queries that exposed a regression rather than replacing them with easier ones.

The [retrieval evaluation article](/blog/evaluate-retrieval-separately-from-answer-generation)
describes the next boundary. First establish which authorized documents reach
the answer generator. Then judge what the generator does with them. That order
makes a proposed prompt change, index change or model change much easier to
assess.
