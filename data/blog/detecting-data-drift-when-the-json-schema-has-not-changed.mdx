Some of the most difficult integration failures arrive as perfectly valid JSON.

The fields are present. Types match. The schema validator stays green. Yet a percentage that used to arrive as `0.25` now arrives as `25`, an empty string starts meaning “redacted”, or an identifier that was stable per account becomes stable only per region.

I call this semantic drift: the representation still fits, but the meaning or operating behaviour has moved.

## A schema protects shape, not every promise

[JSON Schema validation](https://json-schema.org/draft/2020-12/json-schema-validation) can express required fields, types, ranges, patterns, and conditional structure. I use it at the boundary. I do not ask it to prove facts it cannot observe.

These changes may all pass the same schema:

```text
price unit changes from cents to dollars
timestamp changes from event time to processing time
null changes from unknown to deleted
enum frequency moves from 1% to 80%
IDs remain strings but become reusable
array order stops carrying priority
records arrive six hours later
relationships reference entities not yet visible
```

Some can be constrained more tightly after discovery. Others require monitoring across records or time.

## The first drift I look for is contract drift

Before statistics, I check explicit semantic invariants:

```text
currency is present whenever amount is present
start_time <= end_time
provider ID maps to one canonical entity per namespace
version never decreases for one entity
deleted records never return as active without a new lifecycle ID
every referenced parent arrives within the allowed window
```

These checks produce named failure reasons. A sudden increase in `VERSION_REGRESSION` is easier to investigate than a generic anomaly score.

My article on [schema-valid impossible states](/blog/a-valid-schema-can-still-represent-an-impossible-business-state) separates structural, domain, stored-state, authorization, and external invariants. Drift monitoring watches how often those boundaries are approached or crossed.

## Distribution changes are evidence, not automatically defects

I keep baselines for fields where population behaviour matters:

- null, missing, empty, and default rates;
- enum frequencies, including unknown values;
- numeric quantiles and out-of-range counts;
- string length and normalized-pattern changes;
- unique-to-total ratio and duplicate rate;
- records per tenant, region, and endpoint;
- event delay and out-of-order rate;
- relationship coverage.

A holiday, new customer, or product launch can legitimately change these distributions. I alert first on consequence and sustained change, then investigate context.

I avoid a single global baseline. Tenant mix can change while every tenant behaves normally. Source version, endpoint, region, and mapping version are often the useful comparison slices.

## Units deserve redundant checks

Unit changes are especially destructive because values remain numeric.

I carry unit in the contract or type when possible:

```json
{ "amount_minor": 2500, "currency": "EUR" }
```

Then I monitor realistic bounds and ratios:

```text
median amount changes by 100x
fractional values appear in an integer-minor-unit field
currency disappears while amount remains
same product changes price beyond reviewed threshold
```

No statistical test can tell me the correct business unit alone. It can tell me that the old interpretation became implausible before corrupted values spread everywhere.

## Timing drift can hide behind current payloads

If the provider starts batching updates, every record may be correct when it arrives and still violate the product's freshness promise.

I track source event time, observation time, processing time, and product visibility separately. The [data-freshness SLO](/blog/an-slo-for-data-freshness-is-not-an-http-availability-slo) defines the end-to-end user promise; drift metrics explain whether source delay, backlog, or projection changed.

A schema cannot notice that a valid timestamp is now always rounded to midnight or increasingly arrives out of order.

## I attach drift to versions and deployments

Every observation includes safe dimensions:

```text
provider and endpoint
declared API/schema version
mapping version
application deployment
source region
event-time window
```

When unknown enums rise after a provider API release, this correlation shortens the investigation. When the change begins after our mapper deployment, I look inward first.

I do not log payloads to obtain these dimensions. Aggregates, reason codes, safe sampled record references, and controlled evidence are enough.

## Baselines need lifecycle

A baseline can become stale and normalize a defect. I version it, record its training window, and review updates.

My process is:

```text
observe candidate change
classify expected or unexplained
update contract/invariant if meaning changed
repair historical data if needed
approve a new baseline
keep old and new evidence around the transition
```

Automatically teaching the monitor that every sustained change is normal eventually removes the monitor's value.

For low-volume fields I prefer exact constraints and longer windows. Percentage alerts over five records create noise. For high-risk invariants, one violation can be enough.

## A useful alert names the suspected promise

Instead of:

```text
drift score = 0.83
```

I want:

```text
provider north / price.amount_minor
median increased 96x against previous four Tuesdays
currency distribution unchanged
began after source API version 2026-12-24
318 affected records, writes quarantined
```

The alert gives an operator a safe action: pause mapping, quarantine affected records, compare official contract, and reconcile after the interpretation is corrected.

## The test I keep

I replay a clean fixture stream, then inject changes without altering JSON types:

1. Multiply units by 100.
2. Convert missing values to empty strings.
3. Repeat identifiers across namespaces.
4. Delay one partition.
5. Reverse array order.
6. Add an unknown enum gradually.
7. Break parent references temporarily and permanently.

I verify which controls reject, quarantine, warn, or wait. Not every anomaly should stop the pipeline, but every high-consequence semantic change needs a defined response.

Schema validation remains my first gate. Semantic monitoring is the next layer: it watches the meanings, distributions, relationships, and time promises that valid JSON can quietly stop respecting.
