The first AI cost surprise I worry about is not an expensive prompt. It is a cheap call inside a loop.

One user request becomes a planner call. The planner selects twelve records. Each record starts an extraction call, two retries are allowed, a verifier checks every answer, and a tool fetches extra context. Every individual decision looks reasonable. The whole task has no economic boundary.

When I build this kind of workflow, I now define the task budget before I optimize a single prompt. Token optimization comes later.

## A token limit is not a cost budget

Providers report token usage for model calls. OpenAI, for example, exposes usage on API responses and maintains separate [rate-limit guidance](https://developers.openai.com/api/docs/guides/rate-limits). Both are useful inputs. Neither describes the cost of my complete product operation.

My budget includes:

```text
model input and output
retrieval and reranking
tool or external API calls
retry and fallback attempts
compute and queue time
human review, when required
```

It also has non-money limits:

```text
maximum elapsed time
maximum model calls
maximum external side effects
maximum records examined
```

A task can stay below its token allowance and still call a paid search API one hundred times. It can be cheap in money and unacceptable in latency. “Budget” is plural even if I store it in one object.

## I reserve before I spend

The useful model for me is reservation and settlement.

Before starting a step, the workflow estimates its upper useful cost and reserves capacity. After the step, it records the actual spend and releases the difference.

```text
task budget:          $0.40
planner reservation: $0.03
retrieval reserve:   $0.02
8 workers reserved:  $0.24
verification reserve:$0.08
remaining margin:    $0.03
```

The numbers are examples, not universal pricing. The property I want is that fan-out cannot begin if its worst acceptable case already exceeds the task boundary.

I keep this decision in workflow code, not in a dashboard alert that arrives after money was spent.

## The budget object travels with the task

In a distributed workflow, a global daily limit is too far away from the decision. Each worker needs a view of the remaining task budget.

```json
{
  "task_id": "task_8f2",
  "money_limit_minor": 40,
  "model_calls_limit": 16,
  "tool_calls_limit": 10,
  "deadline_ms": 12000,
  "reserved_minor": 27,
  "spent_minor": 9
}
```

I use minor currency units or another fixed representation rather than binary floating point for accounting. Every reservation has an idempotent identity, because a retried worker must not reserve twice.

The ledger can be small:

```text
reserve(step_id, estimated_cost)
settle(step_id, actual_cost)
release(step_id)
remaining(task_id)
```

Atomicity matters. If ten workers read the same remaining amount and then spend independently, the budget is only decoration.

## Estimation is allowed to be imperfect

I do not need a perfect token forecast. I need a conservative estimate, an observed result, and a policy for estimation error.

For a model call I estimate from input size, maximum output, model price, and expected cached portion. For a branch I include its retry ceiling. For fan-out I reserve by batch, then release as work completes.

The estimate and actual usage go into the trace:

```text
ai.budget.estimated_cost
ai.budget.actual_cost
ai.budget.remaining
ai.budget.stop_reason
```

This connects naturally with [tracing an AI workflow across models and tools](/blog/trace-an-ai-workflow-across-retrieval-models-and-tools). Without the task identity, a provider usage graph cannot tell me which product operation created the spend.

## What happens when the budget becomes small

“Stop” is one policy, but it is not the only policy. I define degradation in advance:

1. Reduce optional fan-out.
2. Skip a second-pass stylistic rewrite.
3. Use a cheaper model only if its quality is evaluated for this task.
4. Return a partial result with an honest status.
5. Queue expensive completion for explicit approval.
6. Stop before an irreversible tool call that cannot be verified.

I do not silently switch models just because the remaining money is low. Routing changes quality, context limits, tool behaviour, and sometimes data residency. A cost fallback is still a product decision.

## Retry budgets belong inside cost budgets

Retries are where a bounded request quietly becomes unbounded. I allocate attempts to the task, not independently to every layer.

If the HTTP client retries three times, the model SDK retries twice, and the workflow retries the whole step twice, one intended call can multiply badly. My trace records the logical call and every physical attempt underneath it.

For ambiguous tool outcomes, spending another model call may not be the priority. I first reconcile whether the effect happened. Cheap duplicate actions are still wrong actions.

## Metrics that help me decide

Average cost per request hides the requests I need to understand. I monitor:

- cost per successful task at p50, p95, and p99;
- cost by task type and tenant plan;
- abandoned cost on failed or cancelled tasks;
- retry and fallback cost;
- reserved versus settled cost;
- quality and completion rate by budget band;
- tasks stopped or degraded by policy.

Then I optimize. Maybe the biggest saving is prompt caching. Maybe it is avoiding duplicate retrieval, reducing fan-out, or removing a verifier that catches nothing. Token shaving is valuable only after the trace shows where the task spends.

## The product question comes first

A useful budget starts with: what is this outcome worth, and what promise did I make to the user?

I cannot answer that from a model price table. But once the product gives me a boundary, I can make it executable: reserve before fan-out, settle from actual usage, include retries and tools, and degrade explicitly.

This is how I keep AI engineering close to ordinary engineering. The model is probabilistic, but the system around its spending does not need to be vague.
