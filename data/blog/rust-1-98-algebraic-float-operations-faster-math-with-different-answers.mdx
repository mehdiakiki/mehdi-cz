I like performance work when the contract is written before the benchmark. Rust 1.98's algebraic floating-point operations make this especially important, because the optimization permission is part of the API.

The new methods include `algebraic_add`, `algebraic_sub`, `algebraic_mul`, `algebraic_div`, and `algebraic_rem` for `f32` and `f64`. They look like longer ways to write `+`, `-`, `*`, `/`, and `%`. They are not aliases.

They tell the compiler: for this operation, you may use algebraic rules of real numbers even where floating-point numbers do not follow those rules.

## The small example that explains the difference

Consider four `f32` values:

```rust
fn strict_sum(a: f32, b: f32, c: f32, d: f32) -> f32 {
    ((a + b) + c) + d
}

fn algebraic_sum(a: f32, b: f32, c: f32, d: f32) -> f32 {
    a.algebraic_add(b)
        .algebraic_add(c)
        .algebraic_add(d)
}
```

The ordinary version describes a particular sequence of rounded operations. The algebraic chain may be regrouped, for example as `(a + c) + (b + d)`. That can shorten a dependency chain and make vectorization possible.

With real arithmetic the two forms are equal. With finite floating point they may round differently.

The official [`f32` algebraic-operator documentation](https://doc.rust-lang.org/stable/std/primitive.f32.html#algebraic-operators) goes further: the compiler may combine or rearrange operations, turn division into reciprocal multiplication, and disregard the sign of zero. Precision is not fixed, and NaN or infinity may behave in surprising ways. The operations still never create undefined behaviour by themselves.

## Why Rust made permission explicit

I prefer this API over a project-wide “fast math” switch. A global switch makes it difficult to know which calculations accepted relaxed behaviour. A method call leaves the decision in the source.

In one codebase, I may have both:

```text
vector similarity score       approximate behaviour accepted
money or quota calculation    exact integer/fixed-point contract
protocol fingerprint          reproducible bits required
rendering transform           visual tolerance accepted
safety threshold              edge behaviour must be reviewed
```

The correct choice is local to the calculation, not to the programming language.

Rust 1.98 stabilised these methods as listed in the [official release notes](https://doc.rust-lang.org/releases.html#version-1980-2026-08-20). They are also `const`, but const evaluation does not turn a relaxed numeric contract into an exact one.

## Faster is a hypothesis, not the method name

I would not replace every operator and announce a speedup. Algebraic freedom *may* unlock vectorization. The optimizer still depends on target CPU, loop shape, alias information, compiler version, and surrounding code.

My benchmark keeps three implementations:

```text
baseline ordinary operations
algebraic operations
an algorithmic alternative, when one exists
```

For a reduction, I generate several input families:

- uniform small values;
- values with very different magnitudes;
- cancellation around zero;
- positive and negative zero;
- NaN and infinities;
- realistic production-shaped distributions.

I compile with the actual release profile and target CPU used in deployment. I inspect generated assembly or LLVM output to confirm whether vectorization happened. Wall-clock numbers alone cannot tell me why a version became faster.

```bash
RUSTFLAGS="-C target-cpu=native" cargo bench
cargo rustc --release -- --emit=asm
```

The second command needs adapting when the package has several targets, but the idea is stable: measure the deployed shape and inspect the code that explains the measurement.

## I test an error contract, not exact equality

An algebraic implementation should not reuse the strict implementation's bit-for-bit golden output. That would either fail legitimately or prevent the optimization from changing anything useful.

I define the acceptable error for the product:

```text
absolute error <= A
relative error <= R
classification agreement for finite/NaN/infinite inputs
monotonicity where the domain requires it
decision boundary does not move beyond D
```

The last line is often more important than average numeric error. If a score decides whether an operation is approved, a tiny change close to the threshold can change the product result.

For deterministic replays or cross-machine hashes, I keep ordinary operations and explicitly controlled algorithms. The Rust documentation says the same inputs may produce different results even within one program run because optimization choices are unspecified. Unsafe code must never rely on an algebraic result for soundness.

## A compensated algorithm can be the better answer

Sometimes the real requirement is accuracy, not strict source order. Reassociation for speed is different from using pairwise summation, Kahan summation, or a higher-precision accumulator.

I compare algorithms before choosing compiler freedom. A numerically better algorithm may be fast enough and more stable. Conversely, a similarity search over millions of vectors may accept bounded score movement in exchange for useful SIMD throughput.

There is no “fast math person” and “correct math person” here. There is a written numeric contract.

## My review checklist

Before accepting `algebraic_*`, I ask:

1. Which user-visible decision consumes this result?
2. Are NaN, infinity, and signed zero meaningful?
3. Does another system require bitwise reproducibility?
4. What absolute, relative, and boundary error is acceptable?
5. Did the target build actually vectorize or improve latency?
6. Are tests property-based across difficult values?
7. Can any unsafe invariant or array index depend on the result?

If the seventh answer is yes, I redesign. A floating result with explicitly unpredictable optimization behaviour cannot carry memory safety.

My main lesson from Rust 1.98 is not “use these methods for faster floats.” It is more useful: Rust now lets me mark the exact arithmetic where I accept real-number transformations. That can unlock performance, but only after I have described what a correct answer means for the system I am building.
