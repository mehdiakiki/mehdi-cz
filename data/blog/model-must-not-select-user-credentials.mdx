The tool accepts a user ID and an operation. The model chooses both. The backend loads that user's provider token and performs the operation.

That is an authorization boundary controlled by generated arguments.

The model can help select a target account when the product supports several accounts. It cannot grant itself access to whichever account it names. Credential resolution belongs to trusted application code.

## Keep identity outside the generated arguments

The authenticated request establishes the actor. The server resolves the actor's allowed accounts and the authority for the requested action. Only then should it obtain the relevant secret.

A Rust interface can make the separation visible:

```rust
struct ToolArguments {
    target_account_id: String,
    record_id: String,
}

struct ActorContext {
    authenticated_actor_id: String,
    session_id: String,
}
```

ToolArguments can come from model output after validation. ActorContext must come from the trusted session path. A function that deserializes both from the same model-generated JSON has only renamed the problem.

Treat target_account_id as a requested resource. Check it against the actor's current grants for the exact action. Do not resolve a more privileged default account when lookup fails.

The [authorization-through-tool-calls article](/blog/carry-user-authorization-through-every-ai-tool-call) follows this context across a workflow. The credential lookup is a particularly important point because the selected secret can make an otherwise denied action succeed.

## Recheck at the effect boundary

A long workflow may pause in a queue or wait for approval. Access can change during that time. Revalidate the relevant grant before the external effect, using the policy's freshness requirements.

Background jobs need an explicit identity too. They may act for a user, a service account, or a bounded delegated grant. Record which one and why. “The job has no browser session” is not a reason to use an unrestricted administrator token.

OWASP's [authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) recommends checking permission for each request. Carrying an actor ID in a trace is useful, but it is not the same as enforcing that actor's authority.

## Test the secret that was actually selected

Use a fake credential store that returns distinguishable test handles for different accounts. Ask for an allowed account and assert that the expected handle reaches the mock transport.

Then request another user's account, an unknown account, and an account whose grant was revoked after planning. Assert denial before credential use and no external call.

Avoid logging token values to prove this. Record a non-secret credential reference or have the fake transport inspect a test-only handle.

## Selection can be a real product feature

An operator may legitimately choose among several authorized accounts. Offer those choices and validate the selected identity. The server still decides which credential can be used for which action.

That boundary should stay the same whether the account was selected in a dropdown, written in a prompt, or returned by a model. Generated text is a request to act, not a credential delegation mechanism.
