Many data structures and algorithms interviews test whether somebody has already seen the problem. Once the pattern is recognized, the discussion becomes a typing exercise.

That format was weak before coding assistants. It is weaker now.

These five problems are designed around **constraint ladders**. The first version is familiar enough to enter quickly. Each follow-up changes an assumption that the previous solution depended on. The useful signal is not whether somebody remembers a heap or a hash map. It is whether they can name the invariant, notice an impossible requirement, and adapt without hiding the new cost.

"AI-resistant" is a description of the format, not a permanent property of these exact questions. The explanations are public. An interviewer should generate variants from them; a candidate should use them to practise reasoning, including reasoning about AI-generated proposals.

No implementation language is required. Pseudocode and diagrams are enough when they make the invariant clear.

## Problem 1: an LRU cache where entries also expire

Design a cache with:

- `get(key)`;
- `put(key, value, ttl)`;
- a maximum capacity of `C` live entries;
- least-recently-used eviction;
- independent expiration times;
- an update that may replace both value and TTL.

The ordinary LRU answer combines a hash map with a doubly linked list:

- the map finds a node in average `O(1)` time;
- the list orders nodes from most to least recently used;
- `get` moves a live node to the front;
- capacity eviction removes the tail.

TTL introduces a second ordering. Recency order cannot also answer "which item expires first?" because an old item may have a long TTL and a recent item may expire in one second.

One honest design uses three structures:

1. A hash map from key to the current cache node.
2. A doubly linked list for recency.
3. A min-heap of expiration records ordered by deadline.

Each cache node carries a generation number. Every insert or TTL update pushes `(deadline, key, generation)` into the heap. When an expiration record reaches the top, compare its generation with the current map entry. A mismatch means the heap record is stale and can be discarded.

Before a capacity decision, prune expired heap records and remove the corresponding live nodes. On `get`, also compare the requested node's deadline directly; it may be expired even when another stale record sits at the heap top.

The complexities are:

- average `O(1)` map lookup and list movement;
- `O(log n)` expiration-heap insertion;
- amortized heap cleanup because each expiration record is removed once;
- extra stale records when TTLs are updated repeatedly.

A candidate who promises strict `O(1)` for every operation has probably ignored arbitrary expiration order. Approximate timer wheels, bucketed expirations, background cleanup, or relaxed TTL precision can change the tradeoff, but each changes the requirements too.

**Constraint ladder:**

1. Expiration may be lazy: remove only when a key is touched or capacity is needed.
2. Expired values must disappear within 100 milliseconds even when the cache is idle.
3. Reads happen concurrently and must not wait for global cleanup.
4. The process restarts, but TTL must still make sense.

Each step introduces clocks, coordination, persistence, or approximation. There is no free flag to add to the original LRU.

## Problem 2: "top K" is two different problems

You receive an unbounded stream and may keep only `O(k)` values in memory. Return the top `k` items.

The question is deliberately incomplete. "Top" may mean the largest numeric values or the most frequent identities.

### If top means largest values

Maintain a min-heap of at most `k` values:

- insert until it has `k` items;
- for every later value, compare it with the minimum;
- replace the minimum when the new value is larger.

The heap contains the largest `k` values seen so far. Time is `O(n log k)` and memory is `O(k)`.

The invariant is simple: every discarded value is no larger than the smallest retained value at the moment it is discarded. Because that threshold never decreases, a discarded value cannot belong in the final top `k`.

### If top means most frequent identities

Exact frequency needs a count for every distinct identity that could later become frequent. With an unbounded number of distinct keys, exact results cannot generally be guaranteed with only `O(k)` memory.

This is the important answer. Do not quietly solve "largest values" when the product means "most frequent products."

The requirements must move:

- allow memory proportional to the number of distinct keys;
- bound the key universe;
- accept an approximate heavy-hitters algorithm such as Space-Saving;
- use external storage;
- or define a finite window.

**Constraint ladder:**

1. Return the largest values, duplicates included.
2. Return distinct largest values.
3. Return the most frequent keys exactly.
4. Return approximate heavy hitters with a stated error bound.
5. Merge partial summaries produced by multiple machines.

The data structure is not selected until "top" and "correct" have precise meanings.

## Problem 3: a sliding-window median with duplicates

Numbers arrive continuously. After every arrival, return the median of the last `w` numbers.

For a growing stream without deletion, two heaps work well:

- a max-heap contains the lower half;
- a min-heap contains the upper half;
- their logical sizes differ by at most one;
- every lower value is no greater than every upper value.

The sliding window makes old values leave. Most binary heap interfaces remove only the root efficiently. Searching for an arbitrary expired value would cost linear time.

A common repair uses **lazy deletion**:

1. Keep the two heaps.
2. Keep a map from value to the number of pending deletions.
3. Track each heap's logical size separately from its physical array length.
4. When an old value leaves, mark one occurrence for deletion and decrement the logical size of the heap it belongs to.
5. Whenever a marked value reaches a heap root, remove it and decrement its pending count.
6. Rebalance using logical sizes, then prune roots again.

Duplicates are the detail that breaks many nearly-correct solutions. A deletion record must represent a count, not a Boolean. Physical heap sizes include stale elements, so using `heap.length` for balance eventually returns the wrong median.

The target complexity is `O(log w)` amortized per update with `O(w)` storage. Lazy elements may remain below the root for a while, but every inserted heap entry is physically removed at most once.

**Constraint ladder:**

1. The window size is fixed.
2. The window is based on timestamps, and events may arrive late.
3. The median must be approximate, but memory is much smaller than the window.
4. Results must be merged across partitions.

By the fourth step, two local heaps are no longer the whole design. Approximate quantile sketches and event-time policy become more relevant than heap syntax.

## Problem 4: intervals that can be added and removed

Maintain half-open intervals `[start, end)`. Support:

- add an interval;
- remove a previously added interval;
- query how many intervals cover a point;
- optionally report the maximum overlap anywhere.

For a fixed batch, a sweep line is straightforward. Add `+1` at every start, `-1` at every end, sort events, and take prefix sums.

For dynamic updates, keep the event deltas in a balanced search tree ordered by coordinate. Augment every tree node with:

- the sum of deltas in its subtree;
- the maximum prefix sum inside its subtree.

Adding `[a, b)` changes the delta at `a` by `+1` and the delta at `b` by `-1`. Removal applies the inverse changes. Zero-valued event nodes may be deleted.

To query coverage at point `x`, accumulate subtree sums while walking the search path through coordinates up to `x`. This is `O(log n)` in a balanced tree.

To report global maximum overlap, read the root's augmented maximum prefix. Recomputing that field after rotations requires a precise combine rule:

```text
subtree_sum = left.sum + node.delta + right.sum

subtree_max_prefix = max(
    left.max_prefix,
    left.sum + node.delta,
    left.sum + node.delta + right.max_prefix
)
```

Empty-subtree conventions must be stated. So must the endpoint policy: `[start, end)` avoids counting two touching intervals as overlapping.

**Constraint ladder:**

1. Coordinates are small bounded integers: an array or Fenwick tree becomes possible.
2. Coordinates are large but known ahead of time: coordinate compression helps.
3. Coordinates arrive online: a dynamic tree is needed.
4. Queries ask for the first point reaching overlap `m`: use the augmented prefixes to search.
5. Updates and queries are concurrent: the synchronization model now matters as much as the tree.

## Problem 5: keep changing the graph

Find the shortest path from a source to a destination.

The first question should be: what do edge weights mean?

- All edges have equal cost: breadth-first search is sufficient.
- Edge weights are non-negative: Dijkstra's algorithm is appropriate.
- Negative edges exist but no reachable negative cycle: Bellman-Ford can solve the single-source problem.
- The graph is a directed acyclic graph: topological order gives a faster route even with negative weights.
- A reachable negative cycle exists: no finite shortest path exists for affected destinations.

Naming an algorithm without checking its precondition is not a solution. Dijkstra's greedy finalization depends on non-negative weights. Once a node has the smallest tentative distance, a later path cannot make it smaller. A negative edge destroys that invariant.

**Constraint ladder:**

1. One query on a small graph.
2. Millions of queries on a static graph.
3. Edge weights change every minute.
4. The answer may be approximate but must arrive within five milliseconds.
5. The graph is too large for one machine.

The later versions invite preprocessing, indexes, landmarks, hierarchical methods, caching, invalidation, and partitioning. They are no longer solved by swapping one textbook function for another.

## A scoring rubric that rewards engineering

For each problem, I would score six signals:

1. **Clarification:** did the candidate identify the missing definition?
2. **Invariant:** can they say what must remain true after every operation?
3. **Correctness:** can they explain why the algorithm preserves that invariant?
4. **Complexity:** do they count the new structure introduced by the changed requirement?
5. **Failure:** can they construct an input that breaks the tempting solution?
6. **Adaptation:** when a constraint changes, do they revise the model instead of defending the old answer?

AI can still help generate candidates, counterexamples, or test data. The engineer remains responsible for the contract and proof. That is also how these problems resemble production work.
