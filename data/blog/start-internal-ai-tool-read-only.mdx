The proposed assistant can search accounts, update records, send messages, and run a maintenance command. The first product need is simpler: help support staff find the right account.

Start there.

A narrower first release gives the team a smaller set of behaviours to observe. It also avoids making every early retrieval mistake a possible write mistake.

## Offer the capability the workflow needs

Define a search tool with a bounded query and a bounded response. Construct the caller's identity and tenant scope on the server. The model supplies search terms, not the authority to search another account.

This Rust type illustrates that separation:

```rust
struct SearchArguments {
    query: String,
    page_size: u16,
}

struct AuthorizedScope {
    actor_id: String,
    tenant_id: String,
}
```

A trusted request layer constructs AuthorizedScope after authenticating and authorizing the user. A parsed model argument must not be able to construct it by naming an actor.

The [internal AI tool article](/blog/how-to-build-secure-internal-ai-tool) covers the broader service. This rollout should choose one dataset and one useful question rather than exposing every connector already available to the backend.

OWASP's [excessive-agency guidance](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/) identifies unnecessary functionality and permissions as separate sources of risk. Keep both the offered tools and their effective authority small.

## Read-only still has consequences

A read can reveal private data, cross a tenant boundary, or consume an expensive provider quota. The absence of a write verb does not make it harmless.

Test a support user who can read one account and must not read another. Include a document that asks the assistant to search outside that scope. The tool gateway should reject the forbidden target regardless of how persuasive the document is.

Bound result fields and size. A search result should not automatically include private notes or full documents when a title and identifier satisfy the workflow. Avoid putting retrieved content into unrestricted logs.

Keep the identity through pagination and any follow-up lookup. An authorized first search must not lead to an unscoped get-by-ID tool on the next step.

## Define the evidence for a write tool

After the read workflow is useful, name one proposed write action. State who may perform it, what arguments it accepts, which state it can change, and whether approval is needed.

Require tests for invalid arguments, wrong ownership, duplicate attempts, and a changed target between preview and execution. Give external effects an outcome and recovery contract.

Do not add a generic administrative command because several narrow operations would take longer to define. That shortcut makes the permission boundary much harder to review.

## Make the rollout observable

Review failed searches, denied calls, incomplete answers, and cases where the assistant selected the wrong record. Track enough safe metadata to reproduce the failure without retaining every customer's document.

The initial release can be modest and still solve a real support problem. A reliable lookup assistant gives a much better foundation for a later write workflow than a broad assistant whose most interesting behaviour nobody can safely explain.
