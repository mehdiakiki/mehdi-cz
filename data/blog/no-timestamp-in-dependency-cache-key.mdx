The workflow saves a dependency cache after every successful run. The next run restores nothing because the key contains its start time.

The cache is working. The key asks for a new cache every time.

I would separate inputs that affect reuse from identifiers that only describe a run. A timestamp belongs in a log or artifact name when it helps people. It usually does not belong in the identity of unchanged dependencies.

## Describe the reusable state

For a Rust build cache, consider the toolchain, target, profile, relevant flags, and dependency graph. If native dependencies are involved, the operating environment matters too.

A conceptual key might have this shape:

```text
rust-deps-v2 / runner-image / toolchain / target / profile / lockfile-hash
```

This is a design sketch, not a complete GitHub Actions configuration. The exact inputs depend on what paths the workflow caches. A Cargo registry download cache and compiled target artifacts have different compatibility requirements.

GitHub documents [exact and prefix cache matching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching). A broader restore key can provide reusable material even when the full key changes. It does not prove every restored artifact is valid for the new build.

Cargo still needs to inspect its inputs and rebuild what is dirty. The [incremental-cache article](/blog/what-invalidates-rusts-incremental-compilation-cache) explains that layer, while the [fingerprint guide](/blog/why-did-cargo-rebuild-this-crate-fingerprints-and-dirty-reasons) helps investigate unexpected rebuilds.

## Keep correctness inputs out of the blind spot

Removing a timestamp from a dependency key does not mean time can never affect a build. A static site that includes scheduled content may legitimately need a fresh final build when a publication date arrives.

Reuse dependencies where their inputs allow it. Regenerate final output when the final output's inputs change. Do not restore a whole old site and assume a successful dependency-cache hit made today's pages correct.

The same distinction applies to generated files, environment-dependent build scripts, and external schemas. Undeclared inputs are a correctness bug even if the cache makes the workflow fast.

Also keep secrets out of cached paths. A cache is storage with its own access rules, not a private secret manager.

## Verify with comparable workflow runs

Use the existing CI workflow to compare two runs with unchanged dependencies. Record the cache key, restore result, and whether Cargo reused the expected work. Then change one relevant input and confirm the build still produces the correct result.

If builds remain slow after a cache hit, inspect the actual phase. Compilation, linking, generation, and tests can dominate for different reasons. Do not keep changing the key because one total duration looks disappointing.

Cache storage is finite. More detailed keys can create more entries, while overly broad keys can restore little useful state. Choose the scope based on evidence from representative changes.

A per-run key can be appropriate for immutable run artifacts that are never meant to be reused. Call those artifacts what they are. For dependency reuse, give unchanged inputs a chance to meet the same key again.
