The word “replay” sounds reversible. Run old data through the pipeline again, rebuild what is missing, and return to normal.

In systems I work on, replay is one of the operations I treat with the most respect. Old events can send new emails. A corrected mapper can rewrite valid history. A broad query can include records that were never approved. A worker can stop halfway after producing effects.

Before I replay data, I want a manifest that tells the complete intended story.

## The replay has an identity

I create an immutable replay ID before work begins:

```text
replay_id: replay_2026_12_16_01
requested_by: operator identity
approved_by: reviewer identity
created_at: exact instant
reason: missed normalization after mapper defect
```

Every derived event, repair, log, and metric carries that ID. If production behaviour changes during the run, I can separate ordinary traffic from replay traffic.

The request and approval may be the same person for low-risk internal rebuilding. Irreversible effects require stronger separation. I encode this policy instead of relying on memory during an incident.

## Scope must be frozen

“Replay yesterday's failures” is not a stable selection. The failure table can change while the job runs.

I record one of:

- an immutable list of source record identities and versions;
- a source snapshot identifier;
- a query plus transaction/snapshot boundary;
- a cursor interval whose membership is guaranteed stable.

The manifest stores the count and a digest of the ordered identity set when practical:

```json
{
  "source": "landing/events",
  "snapshot": "snapshot_8841",
  "selection": "provider=north AND sequence>8100 AND sequence<=9400",
  "record_count": 1247,
  "identity_digest": "sha256:..."
}
```

This allows the executor to prove it ran the approved set, not a later interpretation of the query.

## Code version is not enough

A deployment commit does not capture every input to interpretation. I retain:

```text
application artifact digest
schema version
mapping/normalization version
reference-data snapshot
tenant configuration version
feature-policy version
model/prompt version, if AI participates
```

There are two legitimate replay modes:

```text
historical: reproduce the interpretation used at the original time
corrective: apply a reviewed new interpretation to old evidence
```

I name the mode. A corrective replay should not pretend to reproduce history; it intentionally changes it.

## Side effects need a line-by-line policy

The most dangerous manifest field is often a vague `dry_run: false`. I list effect classes:

| Effect | Policy |
| --- | --- |
| rebuild search projection | allow |
| update canonical row | compare-and-set by version |
| publish internal event | emit with replay identity |
| send customer email | suppress |
| charge payment method | prohibit |
| call provider write API | review each ambiguous case |

My article on [replaying events without re-sending emails or charging cards](/blog/replaying-events-without-re-sending-emails-or-charging-cards) explains why transport-level exactly-once claims do not replace an effect ledger.

I prefer handlers where pure state derivation and external effects are separate. Then a replay can rebuild data without accidentally executing every historical reaction.

## Idempotency has a retention window

A stable idempotency key helps only while the receiving system remembers it.

The manifest records:

```text
logical operation identity
deduplication store
deduplication retention
source event age
behaviour after retention expires
```

If I replay a two-year-old event into a service that remembers keys for seven days, its original key no longer protects me. I need a replay-specific effect policy or a current-state comparison before writing.

## Dry run produces a diff, not confidence

My dry run executes parsing, mapping, validation, and comparison but stops before committed effects. Its output is structured:

```text
would create: 812
would update: 391
already correct: 31
unknown mapping: 9
would invoke prohibited effect: 4
invalid source evidence: 0
```

I sample each category, especially the small dangerous ones. “Dry run completed” is not approval; the diff is the evidence used for approval.

The executor verifies that the approved manifest hash is still the one being run. Editing selection or policy after approval creates a new manifest revision.

## Progress checkpoints must describe effects

A cursor saying “processed 600 records” is insufficient if some effects committed and others did not.

For each record or bounded batch, I record:

```text
source identity and version
transformation result digest
effects planned
effects committed with operation IDs
verification status
terminal classification
```

The replay can resume from durable completed work. It does not assume the last started batch was rolled back just because its worker disappeared.

I keep concurrency bounded and respect provider rate limits. Replay traffic should not starve live customer work or create a second incident.

## Verification answers the original reason

If the replay existed because 1,247 records missed normalization, success is not “1,247 messages acknowledged”. I query the target invariant:

```text
all selected identities have mapping version 7
no unselected identity changed
suppressed effect count is exactly expected
unknown mappings have repair cases
source and target totals reconcile
```

I record the verification query/version and result in the manifest. For large data I may use checksums to narrow comparison, followed by record-level checks for differences.

## Retention and privacy still apply

Replay evidence can contain sensitive historical data. I keep identities, versions, safe digests, reason codes, and controlled references rather than copying full payloads into logs.

The manifest has its own retention class. Source snapshots may need encryption and shorter retention. Auditability does not mean duplicating every secret forever.

## My preflight questions

Before changing state, I ask:

1. Is the selected record set immutable and reviewable?
2. Do I know which interpretation versions will run?
3. Is every external effect allowed, suppressed, or prohibited explicitly?
4. Will idempotency still work for records this old?
5. Can the job resume after any individual commit?
6. Can it be paused without losing outcome knowledge?
7. What query will prove the original problem is repaired?
8. Who owns the unresolved cases?

A replay is not simply old input moving through current code. It is a controlled migration over historical evidence. The manifest gives it identity, boundaries, and a result I can verify later—especially when I am the person who must explain why we believed it was safe.
