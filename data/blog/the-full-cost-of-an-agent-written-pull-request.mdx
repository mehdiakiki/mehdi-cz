When people talk about the cost of an AI-written change, they usually mean one prompt and one answer. But a merged change has more parts, and the review is one of them.

So I asked a narrow question. What did one merged pull request really cost here, in tokens, retries and review time? And what did the reviews catch?

Pull requests #26 to #32 in this site's repository added 18 articles between November 14 and 18, 2026. Claude Code agents wrote them. On November 25, I read the usage numbers from the session logs and matched them to the pull requests.

## The setup behind the seven pull requests

One main Claude Code session started the work. I call it the coordinator. It started subagents, which are separate agent conversations with their own context:

- Writer agents. They ran the experiments and wrote the drafts and the evidence logs.
- Reviewer agents. Each one started with a fresh context, read the drafts, recomputed the numbers from the raw files, and wrote a list of findings.

Every agent ran on Opus 5.5. The experiments inside the articles also called Haiku, Sonnet and Opus through `claude -p`.

Each pull request had one commit, with two or three articles.

## What I read, and what I did not

Claude Code writes every session to a JSONL file, one JSON object per line. Subagents get their own files. I read only the numbers: input tokens, output tokens, cache reads, cache writes, the model name, the time and the working directory. I did not read the messages, the prompts or the tool outputs. A short script printed totals only.

One detail matters if you repeat this. Claude Code can write the same model answer on several lines, so adding every line counts some answers twice. In the logs of this batch, 3,926 lines held 1,869 answers, and the lines of one answer always had the same token numbers. So I kept one line per answer.

```bash
jq -c 'select(.type == "assistant" and .message.usage)
  | [.message.id, .requestId, .message.model,
     (.message.usage | .input_tokens, .output_tokens,
       .cache_read_input_tokens, .cache_creation_input_tokens)]' \
  session.jsonl | sort -u
```

Leave the timestamp out. The copies of one answer often have different times, so with the time in the row, `sort -u` keeps them all.

A few words about tokens. Output tokens are what the model writes. A cache write stores the start of a prompt for a while, so the next call can read it back as a cache read. A cache read is much cheaper than normal input, but an agent reads its whole conversation again on every call.

## How I matched the logs to pull requests

The logs do not name pull requests. So I matched them by time, and the match is not equally good for every agent.

- Five writer agents made their last call in the two minutes before a pull request was opened (#27 to #31). The drafts of those pull requests were last saved within two minutes of those calls. This match is good.
- Each reviewer agent made its last call within a minute of the time its review file was saved, and each review names the articles it checked. This match is also good.
- For #26 and #32, I matched three writers by elimination and by the times of their experiments. That match is weak. One short helper agent, 8 minutes long, I could not match at all.
- The coordinator worked for all seven, so I did not split its cost.

## The list-price total

I priced the tokens with Anthropic's list prices for Opus 5.5, as the pricing page showed them on November 14, 2026, in USD per million tokens: 4 for input, 5 for a 5-minute cache write, 8 for a 1-hour cache write, 0.20 for a cache read, and 20 for output. My account is a subscription, so this is a list-price equivalent, not a bill.

| Part                                        | Model calls | List-price equivalent | Share of agent cost |
| ------------------------------------------- | ----------- | --------------------- | ------------------- |
| Coordinator                                 | 242         | USD 43.58             | 22%                 |
| 8 writers and 1 helper                      | 1,299       | USD 132.38            | 66%                 |
| 8 reviewers                                 | 321         | USD 23.77             | 12%                 |
| All agents                                  | 1,862       | USD 199.73            |                     |
| Experiment runs, as reported by Claude Code | 2,613 runs  | USD 19.81             |                     |
| Total                                       |             | USD 219.54            |                     |

That is about USD 31 per merged pull request, and about USD 12 per article.

## Where the tokens went

The agents used 483 million tokens. Almost all of them, 97.5 percent, were cache reads. Output was only 2.6 million tokens, about half a percent.

But the money is spread differently. Cache reads were 47 percent of the cost, cache writes 26 percent and output 26 percent. Uncached input was almost nothing: 3,835 tokens in total.

Why so many cache reads? Each coordinator call read about 479,000 tokens from the cache on average, and each call of a writer or the helper about 245,000. The coordinator's average grew from about 206,000 tokens per call in its first 24 minutes to about 765,000 in the hour of the sixth merge (#31). So in this batch, almost half of the money paid for reading the same conversation again, and almost three quarters went to the cache. In [cost per completed task](/blog/cost-per-completed-task-for-ai-models), about 9,700 tokens came with every call. Here the context that came with every call was 20 to 80 times bigger, and it grew.

The agents wrote about 146,000 output tokens per article. The 18 merged files have 36,828 words in total, with frontmatter and code. So most of the output was not article text. Output also counts the model's thinking and its tool calls, and the writers also wrote experiment scripts and evidence logs.

## Retries and waiting

**CI.** Every pull request had one commit and five checks. All 35 checks passed the first time, so there was no CI retry. The checks took between 233 and 299 seconds per pull request.

**Open to merge.** Between 5 seconds and 325 seconds. Four of the seven were merged 5 to 9 seconds after they were opened, before any of their five checks finished. The checks passed 4 to 5 minutes later. The repository does not require checks before a merge, so CI could not have stopped any of the seven.

**The long wait.** No logged model call succeeded between 23:20 and 06:02 UTC, for 6 hours and 41 minutes. In that gap, Claude Code wrote 50 log entries itself, with the model name `<synthetic>` and zero tokens. I did not open them, so the logs alone do not say why. But the article on [background AI work](/blog/move-the-ai-work-nobody-waits-for-out-of-the-request), from the same night, recorded the weekly usage limit in its own runner, with a reset at 6am UTC. The first successful call came two minutes after that.

From the first call at 21:36 to the sixth merge at 07:19, 9 hours and 43 minutes passed. Without the pause, it was about 3 hours. In the same gap, 228 experiment runs ended in an error. If the pause was the weekly limit, as the other runner recorded, then on a subscription the limit set the pace, not the dollars.

**Review rounds.** One article, [the rtk one](/blog/what-rtk-really-saved-in-my-claude-code-setup), got a full review and then a second check of the fixed draft, which found 6 more problems. The others got one review. For all eight blockers, the published article has the corrected text.

## What the reviews caught

The eight review files held 19 article reviews, because one article was reviewed twice. Together they had 171 numbered findings: 8 blockers, 78 "should fix", 84 small ones, and 1 question that only I could decide. One reviewer also found two unfilled template markers in drafts outside its scope.

I gave each finding one label. These are my labels, and another person might sort a few of them differently.

| Kind of finding                                                       | Count |
| --------------------------------------------------------------------- | ----- |
| An inference or a single run written as a fact                        | 53    |
| A claim that the data, the docs or the files contradict               | 42    |
| Wording or structure only                                             | 18    |
| A feeling, memory or plan in my voice that the evidence does not show | 15    |
| A wrong number or count                                               | 14    |
| A missing source, limit or disclosure                                 | 13    |
| A quote or an output not copied exactly                               | 9     |
| Something that contradicts another article in the batch               | 3     |
| Something that would break CI                                         | 2     |
| A choice for the author (1 open question, 1 rating choice)            | 2     |

Only 14 of 171 were wrong numbers. The reviews list long rows of numbers that they recomputed and found correct. The errors were mostly in the sentences around the numbers. One draft said that an rtk bug was fixed, and the reviewer ran the command again: the bug was still there. Another said that two test settings were kept an hour apart, and the request times showed one reading the other's cache 4 seconds later. A cost article said "paid" on a subscription.

Fifteen findings, in 11 of the 18 drafts, put a feeling, a memory or a plan into my voice that no evidence supported. A reader has no way to check such a sentence.

CI ran only on the versions committed after the reviews. And only two of the 171 findings were things that the site's CI checks: links to articles that were not published yet. CI checks the format of an article, not whether it is true.

The review cost USD 23.77 for 171 findings, about 14 cents per finding. I cannot say how many of the findings a reader would have noticed.

## What I could not measure

- **My own review time.** GitHub shows zero reviews and zero comments on all seven pull requests. Nothing recorded whether I read the drafts, or for how long. Four of the pull requests were merged 5 to 9 seconds after they were opened, so for those four the pull request itself was not a review step. So "review time" here means CI time and open-to-merge time only. Elapsed time is not effort, as I wrote about in [measuring the review queue](/blog/the-review-queue-outgrew-the-build-queue). If you want review minutes, you have to log them.
- **The coordinator per pull request.** It worked for all seven at once.
- **Three writers and one helper.** Their match is weak or missing.
- **Some experiment runs.** The USD 19.81 covers only the runs whose output was saved in a form my script reads. It is a lower bound. The 2,613 runs include 235 that ended in an error, most of them during the pause.
- **Planning before this session, and this article.** Neither is in the totals.
- **Missed problems.** Only one article had a second review. The 171 findings are what the reviewers reported, not a count of all problems.
- **The real price.** These are list prices on a subscription account.

## Count your own

1. Read only the usage fields from the session logs, and keep one line per answer.
2. Price cache reads and cache writes on their own lines. In my case they were almost three quarters of the cost.
3. Match agents to changes by time, and write down how good each match is.
4. Measure CI time and open-to-merge time from the API. Log human review minutes yourself, because nothing else will.
5. Count review findings by kind, not only by number. "171 findings" says little. "8 blockers, and 14 wrong numbers out of 171" tells you where to look.

If you plan an AI feature, the same habits apply to [a monthly cost estimate](/blog/estimate-the-monthly-cost-of-an-ai-feature-before-building-it). Write every input down, and keep the measured parts apart from the guessed ones.
