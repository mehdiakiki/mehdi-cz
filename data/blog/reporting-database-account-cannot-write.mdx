A reporting tool needs to read orders. The fastest setup is to reuse the application's connection string.

Now a tool that should calculate totals can also update orders. A query editor, an accidental statement, or a new maintenance feature has more authority than reporting requires.

I would give the reporting process its own identity. That makes the intended boundary visible in deployment configuration and enforceable by the database.

## Grant the report's actual data

For an existing SQL Server system, start with the tables or views the report needs. A narrow reporting schema or a set of views can be easier to reason about than access to every business table.

Microsoft documents [fixed and user-defined database roles](https://learn.microsoft.com/en-us/sql/relational-databases/security/authentication-access/database-level-roles?view=sql-server-ver17). The built-in data-reader role is broad: it is not the same as permission to read one approved report. Check memberships and effective permissions before choosing it for convenience.

A view can also expose more than intended. Review its columns, joins, tenant conditions, and any functions it calls. “The service only runs SELECT” is an application convention, not a complete permission policy.

Use a different credential from migrations and normal business writes. Store and rotate it through the deployment's secret mechanism. Do not put an owner credential behind a read-only checkbox in the interface.

## Prove the negative path with the real identity

First, run the expected report query. Then attempt a prohibited write to a disposable fixture table using the same connection settings.

Keep the expected error in a small assertion helper:

```rust
fn assert_update_permission_denied(error: &tiberius::error::Error) {
    assert_eq!(error.code(), Some(229));
}
```

Then use it on the attempted update. This Tiberius excerpt assumes an already connected reporting client:

```rust
let error = client
    .execute(
        "UPDATE reporting_permission_probe SET value = @P1 WHERE id = @P2",
        &[&9_i32, &1_i32],
    )
    .await
    .expect_err("reporting account must not update the probe");

assert_update_permission_denied(&error);
```

SQL Server documents [error 229 as an object permission denial](https://learn.microsoft.com/en-us/sql/relational-databases/errors-events/database-engine-events-and-errors-0-to-999?view=sql-server-ver17). This probe assumes the fixture table exists and the account lacks UPDATE permission on the table. A column-level denial can use another code; build the fixture for the rule you mean to check. A connection failure must fail this assertion rather than count as successful protection.

Then reload the probe through a separate fixture account and confirm its value stayed unchanged. Keep the allowed report query in the same test so a broken connection cannot make the whole permission check look successful. Cover prohibited INSERT, DELETE, and schema changes separately, using their expected errors.

The [Rust and SQL Server article](/blog/adding-rust-to-a-system-that-already-uses-sql-server) covers the client connection and bound values. This permission exercise requires a real SQL Server instance and the configured reporting identity. Compiling a Tiberius call does not prove the server denies it.

## Read-only does not mean harmless

A report can still expose private data, read another tenant's records, or consume enough resources to disturb normal traffic. Add query deadlines, bounded result sets, concurrency limits, and the correct customer scope.

Decide whether the report needs current data or can use a replica or prepared dataset. A replica changes freshness and operations; it does not excuse missing authorization. Check what lag means for the report's conclusions.

Stored procedures deserve their own review because execution permissions and ownership rules can provide capabilities beyond a plain table grant. Inventory what the reporting identity can execute, rather than only what it can select directly.

The useful target is small and concrete: the deployed reporting account can run its approved reports, cannot modify the protected business data, and cannot read outside its scope. Keep those checks with the report so future features do not quietly widen the account.
