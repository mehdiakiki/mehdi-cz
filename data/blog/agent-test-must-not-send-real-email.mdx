The test prompt says, “This is a simulation. Do not send real messages.” The application still loads its normal mail credential.

That test environment can send real messages. The prompt is asking it not to.

For end-to-end agent tests, remove the real effect capability where it is unnecessary. Let the workflow exercise the send decision against a capture adapter instead.

## Make the environment choose the adapter

Select the adapter using trusted deployment configuration. Do not let generated arguments name an environment, credential, or arbitrary mail endpoint.

A Rust interface can keep capture separate from delivery:

```rust
struct Mail {
    recipient: String,
    subject: String,
    body: String,
}

#[derive(Default)]
struct CapturedMail {
    messages: Vec<Mail>,
}

impl CapturedMail {
    fn send(&mut self, mail: Mail) {
        self.messages.push(mail);
    }
}
```

This example captures the intended effect in memory. A real test adapter should also enforce size limits and expose assertions about the selected recipient and content. Use synthetic addresses and documents.

Do not initialize a production mail client before deciding which adapter to use. Test configuration should fail closed if a production credential or forbidden endpoint is supplied.

The [internal-tool security article](/blog/how-to-build-secure-internal-ai-tool) explains the surrounding gateway. This environment boundary belongs below the model's wording and above any external effect.

## Check the paths around the adapter

A fake send method is not enough if another tool can execute a shell command, call arbitrary HTTP endpoints, or retrieve the production secret. Review the capabilities the test process actually has.

Keep production credentials out of its environment and secret store access. Restrict network egress according to the infrastructure's supported controls. Verify those controls in the test environment rather than assuming an adapter covers every route.

OWASP's [excessive-agency guidance](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/) is relevant here: a tool set can expose more functionality and authority than the workflow requires.

## Exercise the send decision

Run a workflow that should prepare and send a message. Assert one captured message with the expected authorized recipient. Then use a forbidden recipient, missing approval, and a document that asks the agent to send elsewhere.

The denied cases should capture nothing and cause no external request. The [approval-boundary article](/blog/approval-boundaries-for-expensive-external-and-irreversible-ai-actions) explains binding approval to the resolved action.

Also inspect the actual adapter selected by startup configuration. Testing CapturedMail directly does not prove the end-to-end workflow uses it.

## Keep provider delivery as a separate check

A test of `CapturedMail` alone establishes only that the adapter stores a message. It does not check authorization or approval. To test those rules, run the real gateway with the capture adapter and check the recipient, rejected calls, and absence of external requests.

Neither test proves SMTP behaviour, provider authentication, delivery, or inbox placement.

Use a separate controlled provider integration environment when those are the questions. Give it dedicated credentials and approved destinations, with explicit limits.

The useful separation is between deciding to send and possessing the ability to deliver to real people. Most agent regression tests need the first. Giving them the second by default adds a consequence the prompt cannot reliably remove.
