The worker allows three attempts. The SDK allows three attempts. The HTTP transport also retries.

During an outage, a single job can produce many more calls than the person configuring the worker expected. Each layer looks polite on its own. Together they keep asking the same failing service for more work.

The first repair is an inventory. Count actual network attempts, not the retry setting nearest the business code.

## Find the hidden retry owners

Read the client's documented defaults. Check middleware, redirects where relevant, token refresh, connection recovery, and the job runner's redelivery policy.

Some transport retries happen before a request is known to have reached the server. Others repeat an application operation whose outcome is uncertain. They are not interchangeable.

For one logical operation, choose the layer that understands enough context to decide whether another attempt is safe. Disable or constrain redundant policies where the SDK allows it. If layers must retry independently, make their combined ceiling explicit.

The [retry-budget article](/blog/retries-that-respect-retry-after-deadlines-and-a-retry-budget) covers backoff and deadlines. The practical addition here is making every attempt owner visible in one trace.

## Carry an operation deadline

A Rust budget can make the two basic limits obvious:

```rust
struct AttemptBudget {
    remaining: u32,
    deadline: std::time::Instant,
}

impl AttemptBudget {
    fn claim(&mut self, now: std::time::Instant) -> bool {
        if now >= self.deadline || self.remaining == 0 {
            return false;
        }
        self.remaining -= 1;
        true
    }
}
```

This single-owner helper is not a distributed ledger. A concurrent or durable workflow needs coordinated accounting and a deadline representation suitable for crossing processes. A monotonic Instant cannot be serialized as a universal timestamp.

Claim an attempt before starting it. Include the next wait and request timeout in the remaining time decision. A Retry-After value beyond the deadline is a reason to stop or defer durably, not to extend the customer's deadline silently.

## Keep repeated writes recoverable

HTTP's [idempotent-method discussion](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) explains why automatic repetition needs care. For a non-idempotent application write, use the provider's documented duplicate and outcome contract.

A stable operation identity should survive attempts. Regenerating the key for each retry can turn recovery into several separate writes. A timeout after transmission may require lookup rather than another immediate call.

## Count attempts in the test transport

Return a controlled sequence of failures and record every invocation. Run the old nested policy to show its effective ceiling, then the chosen policy to show the intended one.

Add cancellation, an exhausted budget, and a retry delay longer than the remaining deadline. Assert that no further call starts. Use controlled time for the policy and separate integration checks for real socket behaviour.

One owner does not mean one function must contain all error handling. It means one operation has a coherent decision about repetition. The next engineer should be able to answer how many external attempts a job can cause without multiplying three settings by hand during an incident.
