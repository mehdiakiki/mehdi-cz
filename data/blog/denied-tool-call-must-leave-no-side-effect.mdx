The test asks an unauthorized user to update a record. The gateway returns a denial. The test passes.

The handler already wrote the update before checking permission.

This sounds obvious when written in that order. In a real tool wrapper, the write may be hidden in a helper called “prepare,” a default lookup that creates a record, or an adapter that sends a request while constructing its result.

## Find the first effect

Follow the whole call path. Identify where it first writes storage, opens a privileged resource, or sends an external command.

Parse the generated arguments, validate their meaning, and authorize the actor and target before that point. If a preview needs reads, scope those reads too. Validation itself should not quietly trigger a write.

The [tool-argument boundary article](/blog/validate-model-generated-tool-arguments-at-the-boundary) explains the different checks. This article's narrow invariant is about what remains after a rejected call.

A Rust test outline should inspect both the response and the effect:

```rust
let before = store.snapshot();
let result = gateway.execute(&unauthorized_actor, command).await;

assert!(matches!(result, Err(ToolError::Denied)));
assert_eq!(store.snapshot(), before);
assert_eq!(transport.sent_commands(), 0);
```

These fixture helpers must cover the actual storage and adapter used by the gateway. A snapshot of one in-memory map says nothing about a second adapter that already sent an email.

## Separate rejection from uncertain failure

A denied call should not begin the forbidden action. An authorized call can fail after an external system has accepted it. That is a different outcome and may require lookup or repair.

Do not call a failed post-write audit step an authorization denial. The system needs to report that an authorized effect may have happened, not imply that a policy prevented it.

For database-only actions, a transaction can keep authorized related changes together. It cannot roll back an email or a remote provider request. Keep external effects behind an explicit recoverable boundary.

OWASP's [authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) recommends failing safely when checks fail. For a tool, the safe failure has to be visible in state, not just in prose returned to the model.

## Exercise each rejected layer

Use malformed arguments, a validly shaped but impossible amount, an unauthorized actor, a wrong tenant, and an expired approval when the tool requires one.

After each case, inspect the relevant database rows, files, queue entries, and mock external calls. Also include an allowed command that produces the intended effect. A gateway that denies everything is not correct either.

Run one integration check through the real dispatch route. Unit-testing a policy function cannot prove the dispatcher calls it before invoking the adapter.

## Keep policy state current enough

Permission can change between a read and a write. Use a transaction, version check, or other coordination appropriate to the authorization model when that race matters. Document the freshness guarantee instead of claiming a check at planning time remains valid forever.

The model's final explanation is not evidence that enforcement worked. The useful evidence is a rejected call, unchanged protected state, and no forbidden external request. That makes the security claim concrete enough to review.
