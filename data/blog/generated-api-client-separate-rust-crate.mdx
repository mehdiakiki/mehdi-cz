The service contains a large generated client and a small amount of frequently edited application code. Changing a handler seems to make too much compilation happen again.

Moving the client into its own crate is a reasonable experiment. It is not an automatic build-time improvement.

I would make the boundary answer a concrete question: can ordinary service edits reuse the expensive generated part without paying more elsewhere than the split saves?

## Keep the proposed boundary simple

One possible layout is:

```text
workspace/
  provider-client/   generated types and transport bindings
  service/           product logic and handlers
```

The client crate should not depend on the service that consumes it. Put shared input contracts at a deliberate lower layer rather than creating a circular dependency through a convenience module.

Keep generation ownership clear. Either generated source is checked in with a reviewable update procedure, or a declared build step produces it. The split does not fix a generator with hidden inputs.

The [crate-boundary investigation](/blog/the-unit-of-rebuild-when-you-split-a-rust-workspace) explains what becomes reusable and what can still be instantiated downstream. Generic functions and types can carry code-generation work into the consuming crate.

## Measure changes people actually make

Compare the current and proposed layouts with the same generated source, dependency graph, toolchain, profile, and enabled features.

Use at least three edits: a handler-only change, a generated-schema change, and a change to a shared type used by both sides. Include a clean build so the incremental gain is not presented as the whole cost.

Cargo's [timing report](https://doc.rust-lang.org/cargo/reference/timings.html) can show the shape of work through the existing CI workflow. The [slow-build diagnostic guide](/blog/why-is-my-rust-build-slow-a-diagnostic-tree) helps decide whether this boundary addresses the phase that is actually expensive.

Record which crates rebuild and where the time goes. A faster handler edit matters when it matches the team's normal cycle. A one-off warm build that happens to hit a cache is weaker evidence.

## Look at the API crossing the boundary

A narrow client interface can help review and testing as well as builds. It can also add wrappers, feature coordination, and release work.

Do not hide provider-specific error or pagination semantics behind a generic method just to make the crate look clean. The application still needs enough information to recover correctly. Keep the product's stable model separate from generated provider types where that distinction helps.

Watch feature unification and native dependencies. A crate split can change graph structure without removing the heavy dependency from the build you care about.

## Keep the smaller layout when it wins

For a small client, the extra crate may add little reuse and more maintenance. For generated code that changes as often as the handlers, the expected incremental advantage may be small.

There is no need to defend the split after the measurements reject it. Preserve the comparison and choose the simpler layout when its costs are better.

The useful outcome is a boundary supported by a workload and a reason. “More crates compile faster” is too broad. “This boundary lets these common edits reuse this expensive generated code” is something the repository can verify and the next engineer can understand.
