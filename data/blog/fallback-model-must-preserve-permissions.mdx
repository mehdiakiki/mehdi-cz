The primary model request fails. The router selects a fallback client. That client was initialized for an internal administrator demo and has a broader tool context.

The user asked the same question. The application now has different authority because one upstream request failed.

Availability logic must not become an authorization upgrade. Keep the actor and capabilities owned by the workflow, outside model-client defaults.

## Change the transport, preserve the authority

A model client supplies generated output. The tool gateway decides whether the resulting request is allowed. Both the primary and fallback path should use the same trusted operation context.

This Rust sketch shows the ownership direction:

```rust
let generated = match primary.generate(&request).await {
    Ok(output) => output,
    Err(error) if error.allows_fallback() => {
        fallback.generate(&request).await?
    }
    Err(error) => return Err(error.into()),
};

gateway.execute(&operation_context, generated.tool_call).await
```

The context is not read from generated output or replaced by a fallback client's default user. The real implementation must also handle outputs with no tool call, invalid arguments, and multiple calls according to the workflow's contract.

The [authorization-through-tool-calls article](/blog/carry-user-authorization-through-every-ai-tool-call) explains the identity path. Here the failure route deserves the same attention as the normal route.

## Preserve more than the actor ID

Keep tenant scope, target restrictions, enabled tools, approval bindings, deadlines, and remaining budgets. A fallback must not silently restart an operation with a fresh unlimited attempt count.

Model capabilities can differ. If the fallback cannot produce the required structured result or meet a safety requirement, fail or degrade within a tested contract. Do not remove validation to make the fallback answer usable.

External model routing may also change where data is processed. That requires its own product and data-handling decision; identical tool permissions do not settle every routing concern.

OWASP's [authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) supports enforcing permission at each request boundary. The fallback's output is another untrusted proposal to that same boundary.

## Force the fallback in the test

Use a primary transport that fails in a controlled way. Let the fallback propose an operation forbidden to the current actor. Assert denial, unchanged storage, and zero forbidden external calls.

Then propose an allowed operation and confirm it uses the correct account reference and constraints. Repeat with a revoked grant and an exhausted budget.

Inspect the actual dispatch path rather than only comparing two configuration structs. A router can preserve the right fields and still call an older privileged helper downstream.

## Fallback is optional when the contract cannot hold

Some operations should return a clear temporary failure rather than use a less capable path. That is a product choice, not an availability defect by definition.

Record which transport was used and why, without logging secret credentials or full private content. The operator should be able to explain the route and its outcome.

A model failure must not grant the user new authority. Test that where effects happen, including the fallback path that normally runs only during an outage.
