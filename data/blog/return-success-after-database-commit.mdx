The handler sends a success response. A moment later, the transaction fails to commit.

The client has already moved on. It may show a confirmed order, clear a cart, or start another operation that assumes the first write exists. The server cannot take that response back.

This is one reason I prefer a handler whose return value is built after the durable operation it promises. A future created for commit is not a completed commit. A background task that will commit later is not a completed order either.

## Put the acknowledgement after the promised boundary

For a synchronous checkout, await the transaction commit before returning the successful result. In a Rust SQLx function, that boundary is small:

```rust
async fn finish_order(
    tx: sqlx::Transaction<'_, sqlx::MySql>,
    order_id: i64,
) -> Result<i64, sqlx::Error> {
    tx.commit().await?;
    Ok(order_id)
}
```

This function is only the final step. The caller must have checked authorization, stock, and related writes inside the transaction. The [MySQL checkout example](/blog/mysql-rust-stock-reservation-transaction) shows those operations together.

Do not map the returned ID to a successful HTTP response until the function has completed. If commit fails, preserve a useful internal error category and give the client the API's documented failure or uncertain-outcome response. Avoid sending raw database diagnostics.

SQLx's [transaction API](https://docs.rs/sqlx/0.8.6/sqlx/struct.Transaction.html) makes commit an asynchronous operation. The await is part of the result, not optional cleanup after the response.

## A failed response does not prove a failed order

Now reverse the problem. The database commits successfully. The network connection to the client closes before the response arrives.

From the client's view, the request failed. From the database's view, the order exists. There can also be a connection failure while the server is waiting for the commit response, leaving the application unsure what the database did.

Do not tell the client to generate a new identity and blindly submit again. Give the operation a stable request key, define what reuse means, and provide an outcome lookup when the product needs it. The [idempotency article](/blog/idempotency-key) covers that contract.

The useful states are more than success and failure. They may include confirmed, definitely rejected, and not yet resolved. Keep the unresolved case visible until you have evidence.

## Asynchronous acceptance is a different promise

An endpoint can legitimately return before an order finishes processing. In that design, persist the accepted job first and return a job identity. The response promises durable acceptance, not final completion.

HTTP's [202 status](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3) describes an accepted request whose processing is incomplete. A useful API also exposes progress and a final outcome. A task stored only in the web process's memory does not make that promise durable across a restart.

Test three cases separately: rollback before commit, successful commit and response, and successful commit with a lost response. Read the stored order after each one. For the last case, exercise the client's lookup or same-key recovery path.

The goal is a response the caller can trust. Be precise about which fact has become durable before saying that fact is complete.
