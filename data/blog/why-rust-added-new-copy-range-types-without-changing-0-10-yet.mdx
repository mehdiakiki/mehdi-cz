I once tried to pass the same Rust range to two small helpers and got a move error. My first reaction was that it felt unnecessary: both endpoints were integers, so why was the range not `Copy`?

That old irritation is useful for understanding Rust's replacement range types. Rust 1.95 and 1.96 stabilized new types under `core::range` and `std::range`. They can be `Copy` when their endpoint type is `Copy`. But writing `0..10` still creates the old `std::ops::Range` today.

This is not an unfinished rename. It is a compatibility migration that has to cross an edition boundary.

## The two ranges look almost identical

The familiar syntax uses the legacy type:

```rust
let legacy: std::ops::Range<usize> = 0..10;
```

The replacement type is constructed explicitly:

```rust
use std::range::Range;

let modern: Range<usize> = Range::from(0..10);
```

Their debug representation and half-open meaning are familiar: start is included, end is excluded. Their trait behaviour is not identical.

```rust
use std::range::Range;

let numbers = Range { start: 0_usize, end: 10 };
let first = numbers;
let second = numbers; // Works because the replacement Range<usize> is Copy.

assert_eq!(first.start, second.start);
```

The [`std::range::Range` documentation](https://doc.rust-lang.org/stable/std/range/struct.Range.html) says directly that `start..end` is planned to construct this type in a future edition, but does not do so today.

## Why syntax cannot switch in an ordinary release

Changing the type produced by syntax can change which trait implementation is selected, whether code moves or copies a value, and which methods are available. It can affect type inference and public APIs even when the fields look the same.

Consider a function that accepts the old type exactly:

```rust
fn page(bounds: std::ops::Range<usize>) {
    // existing API
}

page(0..10);
```

If a normal compiler update made `0..10` produce `std::range::Range<usize>`, this code would stop compiling. Rust editions provide a controlled place for syntax and inference changes while allowing crates from different editions to link together.

The source documentation for [`core::range`](https://doc.rust-lang.org/stable/core/range/index.html) calls these “replacement range types” and states that they are intended to replace the legacy types in a future edition. That future wording matters: Rust 1.96 made the type available; it did not rewrite the language syntax.

## The stabilization arrived in pieces

The [Rust 1.95 release notes](https://doc.rust-lang.org/releases.html#version-1950-2026-03-05) list the new `core::range` module and `RangeInclusive`. Rust 1.96 stabilized more of the family, including `Range`, `RangeFrom`, and `RangeToInclusive`.

This staged arrival is another reason not to tell the story as “Rust ranges changed in 1.96”. The library gained replacement building blocks. Existing expressions kept their existing meaning.

For the half-open replacement range, conversion makes the boundary visible:

```rust
use std::range::Range;

fn modern_page(bounds: Range<usize>) {}

modern_page(Range::from(0..10));
```

There are `From` conversions between corresponding new and legacy ranges. I prefer using them at one API boundary rather than scattering conversions across business code.

## `Copy` changes how iteration feels

The old range is an iterator. Consuming it moves the range:

```rust,compile_fail
let legacy = 0..3;
let first: Vec<_> = legacy.collect();
let second: Vec<_> = legacy.collect();
```

With a replacement range whose endpoints are `Copy`, moving the value copies it:

```rust
use std::range::Range;

let range = Range::from(0..3);
let first: Vec<_> = range.into_iter().collect();
let second: Vec<_> = range.into_iter().collect();

assert_eq!(first, second);
```

The new range also exposes `iter()`, which creates an iterator from a borrowed range when the endpoint supports stepping. I still avoid relying on implicit copying in code where the reused bounds are not obvious. A named `bounds` value and two iterations are clearer than a clever chain.

## `Copy` is conditional

The derive does not make every `Range<T>` copyable. It requires `T: Copy`.

```rust,compile_fail
use std::range::Range;

let range = Range {
    start: String::from("a"),
    end: String::from("z"),
};

let first = range;
let second = range;
```

This follows Rust's normal structural rule. The range adds no hidden iterator state to the bounds object, but non-`Copy` endpoints remain non-`Copy`.

I mention this because “the new ranges are Copy” is an attractive headline and an incomplete contract.

## Should a library adopt the new type now?

For a new internal API on Rust 1.96 or later, the replacement range can be pleasant, especially when bounds are reused. For a public crate I ask more questions:

1. What minimum supported Rust version do I promise?
2. Do callers naturally write range syntax?
3. Would requiring `Range::from(0..10)` make the API less ergonomic today?
4. Can I accept `impl RangeBounds<T>` instead of one concrete range type?
5. How will I migrate if a future edition changes syntax?

`RangeBounds` can make an input API flexible, but generic bounds also increase monomorphization and sometimes complicate trait-object boundaries. I choose it for semantics, not as automatic future-proofing.

## The test that keeps the story honest

I compile explicit type assertions under the minimum and current toolchains:

```rust
fn legacy(_: std::ops::Range<i32>) {}
fn modern(_: std::range::Range<i32>) {}

fn main() {
    legacy(0..10);
    modern(std::range::Range::from(0..10));
}
```

This tiny fixture proves more than a paragraph saying “ranges are compatible”. It shows exactly which type syntax constructs and exactly where conversion happens.

The part I appreciate is the restraint. Rust gained range values with cleaner `Copy` behaviour without silently changing existing source. We can use the replacement types today, but the familiar syntax waits for the compatibility mechanism designed for language-level changes. That is slower than a rename and much safer for an ecosystem.
