The test starts a worker, sleeps for a short time, and checks its output. It passes locally and fails on a busy CI runner.

Increasing the sleep may make the failure less frequent. It also makes the test slower and leaves the original guess in place: the worker probably finished by now.

I would first ask which event the test actually needs to observe. That event often already has a natural signal.

## Wait for readiness, not a duration

If the test needs a mock server to accept connections, let the server return its listening address after binding. If it needs a worker to reach a certain operation, send a readiness signal there.

For a retry-policy test, use a controlled transport that records calls and returns a chosen sequence of responses. The test should know when the first attempt happened before checking the next one.

Tokio supports [paused time](https://docs.rs/tokio/1.48.0/tokio/time/fn.pause.html) on its current-thread test runtime with the relevant features. Here is a Rust test outline for a client that must refuse a retry beyond its deadline:

```rust
#[tokio::test(start_paused = true)]
async fn retry_after_cannot_extend_the_request_deadline() {
    let transport = ScriptedTransport::retry_after_seconds(30);
    let result = fetch_with_retry(
        &transport,
        std::time::Duration::from_secs(5),
    ).await;

    assert!(matches!(result, Err(FetchError::Deadline)));
    assert_eq!(transport.attempts(), 1);
}
```

The scripted transport and fetch helper belong to the application's test harness; this is not a standalone program. The transport returns a rate-limit response asking for a thirty-second wait. The client has only five seconds available, so it must not start another attempt. For an allowed retry, separately check the recorded attempt times against the configured delay.

The existing [API failure-testing article](/blog/testing-an-api-integration-against-time-retries-and-bad-pages) covers retries and bad pages together. Deterministic timing makes those scenarios easier to inspect.

## A fake clock has a boundary too

Pausing Tokio time does not pause the standard library clock or a remote provider. A library using another time source may ignore the test's clock entirely.

Keep the policy test close to the code that owns the deadline. Inject a clock or transport where necessary. Then use a smaller set of real integration checks for sockets, cancellation, and actual timeout propagation.

Do not assert millisecond precision from a shared CI machine. Check meaningful bounds and recorded ordering. The exact completion time may vary while the important contract remains correct.

## Preserve the assertion that found the problem

When fixing the test, keep the behaviour it was meant to protect. Removing the final assertion or retrying the test until it passes does not explain the failure.

Try the test under delayed scheduling or a deliberately stalled dependency. A readiness signal should still work because it reports a fact rather than predicting a duration. Put a bounded watchdog around the test so a broken signal becomes a clear failure instead of a job that hangs indefinitely.

There are valid timing tests. If the requirement is that a real operation times out, elapsed time belongs in the evidence. Even then, a controlled dependency and sensible tolerance are better than an arbitrary sleep before looking at state.

The goal is a test that waits for the thing it cares about. Once that relationship is explicit, the test usually becomes both faster and easier to trust.
