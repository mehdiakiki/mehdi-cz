Model routing often begins as an `if` statement around price: simple requests use the small model, difficult requests use the large one.

I understand the attraction. I also see a policy engine hiding inside that branch. The selected model changes quality, tool behaviour, context limits, latency, data handling, and sometimes whether the task can be completed at all.

So I make the routing decision explicit and observable.

## Hard constraints come before scoring

I first remove models that cannot legally or technically serve the request:

```text
required region and data policy
required input/output modality
minimum context and output limits
required structured-output or tool capability
tenant/provider restrictions
safety or age policy
current deployment availability
```

Only then do I compare quality, latency, and cost.

A cheap model outside the permitted region is not a low-scoring candidate. It is not a candidate.

```text
candidates = all_models
candidates = filter_hard_constraints(candidates, task)
choice = rank_evaluated_candidates(candidates, policy)
```

This order makes security failures fail closed and keeps an optimization score from overriding them accidentally.

## “Task difficulty” needs an observable definition

I do not ask another model vaguely whether a request looks hard unless that classifier is evaluated too.

Useful routing features can include:

```text
task type
input length and language
number of documents or tool steps
required output schema
risk tier
retrieval confidence
historical failure slice
user-selected quality mode
```

The task type is often more predictive than prompt length. Extracting three fixed fields from a long document may be easier than resolving one short ambiguous instruction.

I keep features safe and avoid routing on protected personal attributes unless there is a justified, reviewed requirement.

## Every route needs an evaluation result

Before enabling a model for a task, I run the same task-specific evaluation set used for releases. OpenAI's [evaluation best-practices guide](https://developers.openai.com/api/docs/guides/evaluation-best-practices) emphasizes defining task criteria and using production-shaped data rather than relying on generic impressions.

My route table contains evidence:

| Task | Candidate | Quality gate | p95 latency | Cost band | Allowed |
| --- | --- | --- | --- | --- | --- |
| classify ticket | model S | pass | low | low | yes |
| extract contract terms | model S | fail on dates | low | low | no |
| extract contract terms | model L | pass | medium | high | yes |
| draft search query | model S | pass | low | low | yes |

I do not fill this table with invented universal numbers. It comes from the application's evaluation set and current deployment measurements.

## A fallback is another route, not an exception

If the preferred model times out, switching models may change output. The fallback candidate needs the same hard-constraint and quality review.

I define:

```text
preferred route
allowed fallback routes
maximum attempts across all routes
conditions that permit fallback
conditions that require stop or human review
```

A safety rejection is not a provider timeout. I do not route around a policy decision by asking another model until one answers.

For tool-using workflows, fallback after a partial trajectory must know which effects already happened. It cannot restart the entire agent blindly.

## The routing decision belongs in the trace

I record a compact decision:

```json
{
  "routing_policy": "support-v12",
  "task_type": "ticket_classification",
  "eligible_models": ["model-s", "model-l"],
  "selected": "model-s",
  "reason": "quality_gate_passed_lowest_cost_band",
  "fallback": false
}
```

Sensitive prompt content does not belong in this event. The trace links to a governed evaluation or fixture identity where needed.

This lets me answer whether a quality regression came from a prompt change, a model update, or a different route. It also connects spend to the decision that created it, as described in [task-level AI cost budgets](/blog/give-an-ai-task-a-cost-budget-before-optimizing-tokens).

## Aliases and model updates can move the road

Provider model names may be pinned snapshots or aliases that evolve. The [OpenAI model documentation](https://developers.openai.com/api/docs/models) exposes model capabilities and identifiers, but my product still has to decide what identity its reproducibility promise requires.

For high-risk tasks, I prefer an evaluated pinned version when available. For lower-risk tasks, an alias may receive useful improvements, but I monitor it as a dependency change.

The routing policy version includes the model identity rule, not only a friendly model name.

## Shadow routing tests decisions without effects

I can send a sampled, privacy-approved task to a candidate route and compare outputs without showing the candidate result or executing its tools.

Shadow traffic is useful for:

- estimating quality by task slice;
- measuring latency and error rate;
- testing a new classifier or threshold;
- detecting model drift before changing the active route.

I avoid duplicating sensitive data without policy, and I never shadow irreversible tools. Candidate outputs are retained only as long as evaluation requires.

After shadowing, a small canary receives real traffic with rollback conditions. Aggregate success can hide one important failure slice, so gates remain task- and risk-specific.

## Capacity is part of routing, but not above truth

When a provider reaches a rate limit, routing to available capacity can protect latency. It should not send the task to a model that failed its quality gate.

The possible outcomes are:

```text
route to another qualified deployment
queue within the task deadline
use the tested non-AI path
return an honest unavailable state
```

My [non-AI fallback article](/blog/design-the-non-ai-path-before-the-model-is-unavailable) covers the last two. Availability pressure does not create a new qualified model.

## What I monitor

I look at quality, failure, latency, and cost by:

```text
routing policy version
task type and risk tier
selected model/deployment
fallback reason
input-size band
tenant plan where appropriate
```

I also track route instability: how often small input changes cross a routing boundary and whether those changes create surprising product behaviour.

The senior engineering work is not writing the `if`. It is defining candidate eligibility, proving quality per task, preserving policy through retries, observing the decision, and keeping a useful outcome when no route qualifies.

That is why I call model routing a policy engine. It optimizes only after it decides what the system is allowed to trade.
