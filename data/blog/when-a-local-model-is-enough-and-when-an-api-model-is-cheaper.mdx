Haiku 5.5 costs USD 0.10 per million input tokens. That is the list price I read on November 14, 2026. At this price, sorting one short support message costs a small fraction of a cent.

So is there still a reason to run a small open model on your own machine? A local model is not free: the machine costs money, and so do wrong answers. Other reasons are privacy, working offline, or a rule about where the data must stay. Those are real, but they are a different question than price.

On November 25 I ran an experiment to separate these questions. I took the exact task from [my routing experiment](/blog/rules-search-small-model-big-model-agent-one-task-measured) and ran it on my laptop with no API at all.

## The task, again

The data is banking77 from PolyAI (CC BY 4.0): online banking questions, each labeled with one of 77 intents. An intent is the reason why the customer writes, like `card_arrival`. I used the same 200 test messages, the same system prompt with the 77 intent names, and the same strict check: the answer must be exactly one of the 77 names. If the first answer is not on the list, I ask once more.

There were two versions in the first experiment, and I repeated both:

- **Intent list:** the model sees only the 77 names. Haiku 5.5 got 134 of 200 right.
- **10 examples:** a small search finds the 10 most similar labeled training messages, and they go into the prompt with their intents. Haiku got 187 of 200 right.

And one result with no model at all: the search itself, with a vote of the five nearest messages, got 171 of 200, in about a millisecond per message.

## What I ran locally

The laptop has a 12th Gen Intel Core i7-1260P (12 cores, 16 threads) and 62 GiB of memory. I used only the CPU. It was not idle: other programs were running, with a load average of about 2 to 3 before my tests started. During the tests it was 3 to 9, including my own runs. So these are speeds of a normal working laptop, not of a clean benchmark machine.

The runtime is llama.cpp v1.0.0. Its release page points to build b12359, and I used that build's official Linux x64 binary (MIT license). Its sha256 matched the checksum that GitHub publishes for the file. The models:

- **Qwen3.5-2B** in the Q4_K_M format from the unsloth repository on Hugging Face. 1.28 GB, Apache 2.0 license.
- **Qwen3.5-0.8B** in the Q8_0 format from the ggml-org repository. 0.83 GB, Apache 2.0.

Both sha256 values matched the values on Hugging Face. A 4B model did not fit on my scratch disk, so the biggest model here is 2B.

The server runs on my machine and listens only on localhost:

```bash
llama-server -m Qwen3.5-2B-Q4_K_M.gguf -t 4 -c 4096 --parallel 1 \
  --host 127.0.0.1 --port 18080 --no-webui -ngl 0
```

My Python client sends one message per request at temperature 0. A retry at temperature 0 would almost always repeat the same text, so the one retry uses temperature 0.7. One more difference: I turned thinking off for the Qwen models, which is their default. Haiku ran through Claude Code at effort medium, with its default sampling and some thinking. The prompt and the check are the same, but the model settings are not. The check is the same as before:

```python
answer = (resp["choices"][0]["message"].get("content") or "").strip()
valid = answer in labels
```

## How fast is a 2B model on a laptop CPU?

First `llama-bench`, the benchmark tool of llama.cpp. "pp512" is reading a prompt of 512 tokens, "tg128" is writing 128 tokens. A token is a piece of a word.

```text
model                     threads   pp512 (tokens/s)   tg128 (tokens/s)
qwen35 2B Q4_K - Medium      4      146.76 ± 6.65      21.06 ± 2.86
qwen35 2B Q4_K - Medium      8      125.05 ± 4.53      13.99 ± 1.62
qwen35 2B Q4_K - Medium     12      156.62 ± 26.66     13.51 ± 0.24
qwen35 0.8B Q8_0             4      222.69 ± 36.65     34.25 ± 4.18
qwen35 0.8B Q8_0             8      123.75 ± 27.32     19.45 ± 2.52
```

More threads did not help. Writing was fastest with 4 threads, so I used 4 threads for everything. I did not test an idle machine, so the other work may be part of the reason. Another possible reason: this CPU has only 4 fast cores, and its other 8 cores are slower. I did not test which reason matters more.

For this task, writing speed matters little, because an answer is about 5 tokens. The prompt matters. The instructions are about 450 tokens and the same in every request, so the server keeps them in its cache. After the first request it reads only the new part: about 34 tokens with the intent list, about 267 with 10 examples.

## The results

| Setup                     | Right of 200 | Mean time per message | Messages per hour | Peak memory |
| ------------------------- | ------------ | --------------------- | ----------------- | ----------- |
| Qwen3.5-0.8B, intent list | 106          | 0.61 s                | 5,915             | 1.1 GB      |
| Qwen3.5-2B, intent list   | 98           | 0.88 s                | 4,083             | 2.1 GB      |
| Qwen3.5-0.8B, 10 examples | 165          | 1.85 s                | 1,941             | 1.5 GB      |
| Qwen3.5-2B, 10 examples   | 167          | 2.84 s                | 1,269             | 2.5 GB      |
| Search only, no model     | 171          | about 1 ms            |                   |             |
| Haiku 5.5, intent list    | 134          | 3.22 s (1.49 s API)   |                   |             |
| Haiku 5.5, 10 examples    | 187          | 2.23 s (0.98 s API)   |                   |             |

Local times are full HTTP requests, retries included. Haiku times come from the first experiment, through Claude Code: the first number includes starting the CLI, the number in brackets is the API time per call, from the saved logs of that experiment. Peak memory is the highest memory use of the server process.

With only the intent list, the small models were far behind: 98 and 106 against 134. The 0.8B model scored higher than the 2B model here, but with 200 messages a difference of 8 is too small to trust. I would not say the smaller one is better.

The strict check caught names that look right but do not exist, like `transfer_policy` and `exchange_fee` from the 2B model. The 0.8B model wrote `refund_not_showing_up`, but the label is `Refund_not_showing_up`, with a capital R. I kept the check strict, as in the first experiment.

With 10 examples, both local models jumped to 165 and 167. That is much better. But it is not better than the search alone, 171, which uses no model. A gap of 4 or 6 messages out of 200 is too small to call either way.

## Did the local model add anything over search?

This was not obvious for me, so I checked the saved results. In 81 of the 200 messages, all five nearest neighbours in the search had the same intent, and search was right on all 81. On the other 119 messages, the 2B model with examples got 90 right. Search also got 90.

So "trust search when its neighbours agree, ask the 2B model otherwise" gives 171, exactly the search result. The 2B model added no accuracy over a millisecond of search.

Sometimes it even made things worse. On 4 of the 81 messages where all five neighbours agreed, the 2B model chose a different, wrong intent. For "How do I exchange my GBP to AUD?" all 10 examples in the prompt had the intent `exchange_via_app`. The 2B model answered `exchange_rate`. It made the same mistake on another exchange message with 10 unanimous examples. The 0.8B model got both right. Haiku got all 81 of the unanimous messages right.

## What it costs

The API side, per 1,000 messages, with list prices of November 14, 2026:

- Haiku, intent list: USD 0.15, as Claude Code reported for my calls. A direct API call is cheaper: my [monthly cost estimate](/blog/estimate-the-monthly-cost-of-an-ai-feature-before-building-it) gives USD 0.10 with no caching, 0.03 with a warm cache, 0.014 with batch and a warm cache.
- Haiku, 10 examples: USD 0.21, as Claude Code reported.

The local side has no bill, but it has two costs that I could not measure. The CPU power counters need root rights, so the energy is an assumption. Replace these assumptions with yours:

- **Assumption:** the laptop uses 30 to 60 W while it runs the job.
- **Assumption:** electricity costs USD 0.30 per kWh.
- **Assumption:** if the machine is used only for this, it costs USD 1,500 and lives 3 years. If you use a laptop that you already have, and it is idle anyway, this part is zero.

The laptop time per 1,000 messages is measured: 14.7 minutes for the 2B model with the intent list, 47.3 minutes with examples.

| Setup, per 1,000 messages | Electricity (assumed) | Machine share (assumed) | Total              |
| ------------------------- | --------------------- | ----------------------- | ------------------ |
| Qwen3.5-2B, intent list   | USD 0.002 to 0.004    | USD 0.014 to 0.042      | USD 0.016 to 0.046 |
| Qwen3.5-2B, 10 examples   | USD 0.007 to 0.014    | USD 0.045 to 0.135      | USD 0.052 to 0.149 |

The low machine share is for a machine that runs all day for 3 years. The high one is for 8 hours a day.

So which is cheaper? With examples, local is USD 0.05 to 0.15 per 1,000 messages. Haiku is USD 0.21 through Claude Code. A direct API call would be about USD 0.05 to 0.12, a rough estimate from the token counts of my runs. The ranges overlap. There is no clear winner on the bill, only a few cents of difference.

But the answers are not equal. Per 1,000 messages, the 2B model with examples sends about 160 to the wrong intent, and Haiku with examples about 60. In the cost estimate I assumed that one wrong route costs 1 to 3 minutes of a support person, at USD 30 per hour. With that assumption, 100 more wrong routes cost USD 50 to 150 per 1,000 messages. That is hundreds of times bigger than the few cents of difference on the bill.

Capacity is not the problem at normal volumes: 1,269 messages per hour is about 30,000 per day.

## Offline, and where the data goes

I checked two simple things. At one moment during a run with the 0.8B model, the server had only two network sockets: its listener on 127.0.0.1 and the connection from my client, also on 127.0.0.1. Then I ran 20 messages in a network namespace with no internet. Inside it, a request to huggingface.co failed with "Could not resolve host". The server and client still worked, and the 20 answers were identical to the run with the network. It only shows that the setup does not need the network.

## So when is a local model the right choice?

On this task, price was not the reason. The API and my laptop cost about the same few cents per 1,000 messages, and the errors cost much more than both.

A local model is the right choice when the data is not allowed to leave the machine, when there is no network, or when a rule says where the data must be processed. Then Haiku is not on the table, and the honest comparison is between local options. Here the winner was plain search, 171 of 200, in a millisecond, with no model. Both local models with examples came close, but neither beat it. And local is not automatically private: as [my browser model article](/blog/could-this-feature-run-entirely-in-the-browser) shows, check the real network traffic.

When the data may go to an API, Haiku with examples beat the best local result by 16 messages of 200, for cents. For this task, it is the better choice.

The limits: one laptop with other work running, one run per setup, 200 messages, two models from one family (Qwen3.5 at 2B and 0.8B), llama.cpp v1.0.0, temperature 0, all on November 25, 2026. With 200 messages, a score can move by about 10 messages either way, and more for the scores near half. Small gaps, like 98 against 106 or 167 against 171, could change with another sample. I did not test a 4B model or several requests in parallel. Energy and hardware costs are assumptions, and the Haiku numbers come from the earlier runs on November 14 and 15.
