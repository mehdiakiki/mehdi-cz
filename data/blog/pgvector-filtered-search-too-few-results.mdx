The query asks for five passages from one customer's documents. PostgreSQL has ten eligible rows. After adding a vector index, the query returns fewer than five.

An AI-generated repair might increase the limit or move the tenant filter outside the retrieval step. Before accepting either change, establish where candidates are lost. The access rule still applies when search becomes approximate.

This investigation keeps the data and the predicate fixed. It compares an exact query, a limited HNSW scan, and an iterative HNSW scan. HNSW is an approximate nearest-neighbor index. It searches a graph of vectors rather than scoring every eligible row.

## First establish that matching data exists

The [Rust lab](https://github.com/mehdiakiki/mehdi-cz/blob/content/ai-writing-evidence-2026-10-31/experiments/rust-backend/tests/pgvector_filter.rs) creates 1,010 three-dimensional vectors. One thousand belong to tenant 8 and lie close to the query vector. Ten belong to tenant 7 and lie farther away.

The numbers are deliberately small and the coordinates are synthetic. They arrange a selective-filter problem. They do not represent a real embedding model, corpus, or production capacity.

The query is stored as a Rust constant:

```rust
const FILTERED: &str =
    "SELECT id FROM filtered_documents WHERE tenant_id = $1 \
     ORDER BY embedding OPERATOR(public.<=>) $2::public.vector LIMIT 5";
```

The caller supplies tenant 7 and the fixed query vector:

```rust
let ids: Vec<i64> = sqlx::query_scalar(FILTERED)
    .bind(7_i64)
    .bind("[1,0,0]")
    .fetch_all(connection)
    .await?;
```

In a real application, tenant identity comes from authenticated server context. Here it is a fixture constant. The same binding and predicate are used in every comparison.

First run the exact path and inspect its plan. The fixture disables index scans within its transaction, requires the plan to contain a sequential scan, and verifies that five rows are returned. This establishes that an empty result is not explained by an empty authorized corpus.

## Inspect the plan before explaining the result

Next, the fixture enables index scans, discourages sequential scans, and sets `hnsw.ef_search` to 40 with iterative scans off. It requires PostgreSQL to use the named HNSW index.

Those planner settings make the experiment observable. They are not a recommendation to disable sequential scans in an application. A small filtered set may be served well by an exact scan. Let production measurements and plans inform that decision.

With an approximate index, PostgreSQL can apply the tenant predicate to candidates produced by the scan. If most nearby candidates belong to other tenants, the scan can exhaust its work before finding enough eligible rows. The predicate does not promise that the index will find five matches.

The [pgvector filtering guide](https://github.com/pgvector/pgvector#filtering) explains this behavior. Its [upstream discussion of a filtered HNSW plan](https://github.com/pgvector/pgvector/issues/1032) also illustrates why plan selection and result completeness need separate investigation. That report is evidence of a real reader problem, not a performance prediction for this fixture.

The test requires the limited scan to return fewer than five rows. If it does not, the fixture has not reproduced the claimed failure. Printing a configuration value without inspecting the actual plan would not establish which search path ran.

## Give the scan more work without widening access

The third path keeps the tenant predicate and turns on iterative scanning:

```rust
sqlx::query("SET LOCAL hnsw.iterative_scan = 'strict_order'")
    .execute(&mut *tx)
    .await?;
```

The fixture then inspects the plan again, requires the same HNSW index, and checks that five tenant-7 rows are returned. It also checks the returned IDs against the fixture's eligible range.

This comparison changes the search policy while preserving eligibility. It does not let the model see foreign candidates and ask it to discard them afterward. The [retrieval permissions guide](/blog/filter-before-retrieval-permissions-are-part-of-relevance) explains why filtering before model and reranker requests matters.

The query runs on a SQLx transaction. The `SET LOCAL` values and the experiment's schema work are rolled back at the end. Avoid casually turning a local experiment into session-wide pool state.

Iterative scanning still has work and memory limits. Getting five rows from this arrangement does not establish that the same settings will fill every result on a different corpus. Nor does `strict_order` mean the selected set is an exact nearest-neighbor answer. Ordering the candidates found and finding all of the true nearest candidates are different properties.

## Compare the questions each path answers

| Path | Evidence to retain | What it establishes here |
| --- | --- | --- |
| Exact search with the same tenant predicate | Plan, bound inputs, returned IDs | Five eligible results exist |
| HNSW with iterative scanning off | Actual index plan and returned count | Limited approximate work can miss eligible results |
| HNSW with iterative scanning on | Actual index plan and eligible IDs | More scan work fills the result for this fixture |

The lab checks pgvector 0.8.7 and SQLx 0.8.6 against the existing GitHub PostgreSQL service. It prints each result and plan. There is no claimed speedup, recall percentage, or latency target from these 1,010 rows.

For a real comparison, retain a reviewed query set and the exact authorized results for the same data revision. Compare approximate results with that reference, including ties and the chosen distance metric. Then measure latency and resource use under the intended concurrency.

The [retrieval evaluation article](/blog/evaluate-retrieval-separately-from-answer-generation) develops relevance testing. A result count is only one symptom. Five irrelevant passages are not a successful retrieval system.

## Choose a serving policy for each workload

An exact search over a small authorized set may be the right choice. Another workload may justify more approximate-search effort. Repeatedly selective filters can motivate a conventional filter index, an appropriate partial index, or partitioning, with their own write and maintenance costs.

Choose from evidence about the actual data distribution and query plan. Increasing every search budget can make one small tenant's request traverse a much larger shared corpus. That needs a resource budget as well as a relevance decision.

Also investigate ordinary reasons a result is absent: missing or stale embeddings, incompatible model configurations, null vectors, and unsupported vector values. Changing an HNSW setting cannot create a missing source passage. The serving contract must still decide whether edited documents remain eligible while embedding work catches up.

If the search remains incomplete within the request budget, give the application an explicit outcome. It might return fewer passages, use an authorized exact fallback, or say that evidence is insufficient. Silently widening access changes the product's contract.

## The acceptance decision

I would accept a proposed repair after seeing the same authorized query find its baseline results, the actual index plan reproduce the shortfall, and a bounded change improve completeness without returning another tenant's rows.

That is more useful than accepting a larger limit because the demo looks better. Keep the data, authorization rule, query plan, and search-work settings together so the next investigation can explain what changed.
