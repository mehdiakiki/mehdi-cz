The same customer asks the same question. The cache returns the same answer. In between, someone revoked access to the document that answer quotes.

The cache lookup can work exactly as written and still return content the customer should no longer receive.

Before adding a result cache, decide what must remain true when an old answer is used. Which task produced it? Which sources supported it? Does this caller still have access, and are those sources still the same versions?

Let's make those questions observable with a small Rust and PostgreSQL example. The answer is a fixed string in this fixture. There is no model call, answer-quality evaluation or hit-rate claim.

## Decide what a hit is allowed to reuse

A question string rarely describes the whole task. The same words can run under another prompt, output format, tool policy, document collection or user identity.

I would start with an explicit task contract:

| Dependency | What needs to match |
| --- | --- |
| Task and input | The same operation and the input normalization it promises |
| Instructions and output | Prompt behavior, required fields and validation rules |
| Model and tools | The chosen model policy and permitted tool behavior |
| Retrieval | The query, search policy and relevant corpus revision |
| Caller | Tenant, principal and the visibility rules for the result |
| Sources | Every source supplied to generation, with its identity and version |

Store dependencies for sources the answer used even when the final text did not cite them. These are inputs to the decision. Hashing them does not establish that they are complete or current. In particular, a stored permission value can be just as stale as a stored answer.

Use an unambiguous key encoding. Keep credentials and private document text out of keys that may appear in logs. The [tenant cache guide](/blog/tenant-in-cache-key-not-only-record-id) follows collisions across tenant and provider-account namespaces.

## A cache key does not notice a source edit

The fixture stores a source document, a grant allowing Alice to read it, and an answer based on that source. The cached value records its tenant, principal, contract version, source ID and source revision.

An unchanged request can reuse the answer. Changing the contract version must produce a miss. Asking as another user or tenant must also miss.

Then the source body changes while the cached value remains in memory. A plain lookup still finds the old answer. Including a tenant and user in the key did not tell the cache that the source changed.

The fixture gives each document a database-owned revision. A trigger assigns a new sequence value before both inserts and updates. It also replaces an explicitly supplied old revision. The writer cannot accidentally preserve the revision when changing the body or recreating a document.

The validator compares the cached revision with the visible row's current revision. The old answer becomes a miss. A newly built value with the updated source can become a hit again.

The version is an identity token, not a count of edits. Sequence gaps are harmless. Reusing the document ID after deletion must also get a new revision; otherwise an old value could match a different document that happened to restart at revision one. The test deliberately supplies the old revision on reinsertion and requires the trigger to replace it.

The [trigger documentation](https://www.postgresql.org/docs/18/sql-createtrigger.html) describes how a before-row trigger can change the inserted or updated row. This is one possible version issuer. An immutable source revision or a suitable content identity can serve the same purpose. Choose an issuer that covers every write path in your system. Adding a `revision` column that some writers ignore leaves the original problem in place. Restoring a database or resetting its version issuer needs a fresh cache namespace; that operation is outside this fixture.

## Check current access before returning the saved text

The full [Rust fixture](https://github.com/mehdiakiki/mehdi-cz/blob/85f6329a6cf36e944adbb4b4890b0f9ff7deb04f/experiments/rust-backend/tests/database_boundaries.rs) defines three small types: `Principal` carries the host's tenant and user, `CachedAnswer` carries the saved dependencies and text, and `CacheUse` distinguishes a hit, a miss and a denied source.

The application first finds a candidate using its complete request key. The function below validates that candidate; key construction is outside this fixture.

Here is its reuse function:

```rust
async fn reuse_answer(
    pool: &PgPool,
    principal: &Principal,
    contract: i32,
    cached: &CachedAnswer,
) -> Result<CacheUse> {
    if (cached.tenant, cached.user, cached.contract) != (principal.tenant, principal.user, contract)
        || cached.sources.is_empty()
    {
        return Ok(CacheUse::Miss);
    }
    let mut tx = pool.begin().await?;
    sqlx::query("SET TRANSACTION READ ONLY")
        .execute(&mut *tx)
        .await?;
    sqlx::query(
        "SELECT set_config('app.tenant_id', $1, true),
                set_config('app.principal_id', $2, true)",
    )
    .bind(principal.tenant)
    .bind(principal.user)
    .execute(&mut *tx)
    .await?;
    let ids: Vec<i64> = cached.sources.iter().map(|(id, _)| *id).collect();
    let visible: Vec<(i64, i64)> = sqlx::query_as(
        "SELECT id, revision FROM cache_source_review.documents
         WHERE id = ANY($1) ORDER BY id",
    )
    .bind(&ids)
    .fetch_all(&mut *tx)
    .await?;
    tx.commit().await?;
    if visible.len() != cached.sources.len() {
        return Ok(CacheUse::Denied);
    }
    if visible != cached.sources {
        return Ok(CacheUse::Miss);
    }
    Ok(CacheUse::Hit(cached.text.clone()))
}
```

The function first checks the caller and contract. It then asks PostgreSQL for the cached sources and their revisions under the restricted reader role.

Row policies limit documents to the current tenant and the principal's current grants. A second policy limits which grants that role can see. If a required source is no longer visible, the function returns `Denied`. If its version changed, it returns `Miss`. Only the remaining path returns the saved text.

This query still does work on a cache hit. That can be a reasonable trade when it avoids retrieval or a model call, but this fixture does not measure the saving. If validation costs as much as rebuilding the answer, reconsider what the cache should store.

The host must obtain the principal from authentication. Alice and the other principals are fixed test identities here. A model argument must not select another user's database context. The [PostgreSQL MCP tool example](/blog/read-only-postgresql-mcp-tool-limits) explains that boundary and the scope of a restricted database role.

The reuse function also propagates database errors. An unavailable permission check is not evidence that the old grant still applies.

## Revoke access while the value stays warm

The [recorded GitHub run](https://github.com/mehdiakiki/mehdi-cz/actions/runs/41247556267/job/124674040829) exercises the following cases:

| Change after a value is cached | Required result |
| --- | --- |
| Caller, contract and source unchanged | Hit |
| Contract version changes | Miss |
| Tenant or principal changes | Miss |
| A claimed source belongs to another user's grant | Denied |
| Source body changes and receives a new revision | Miss |
| Access is revoked while the text remains cached | Denied |
| Source is deleted | Denied |
| The same document ID is inserted again and access restored | Miss |

The revocation case does not evict the cached text first. The bytes remain present. PostgreSQL's current row policy makes the source unavailable to the reuse check, which refuses to return those bytes.

Refusing reuse does not erase the saved bytes. A storage-deletion promise needs its own retention and propagation policy. The example assumes this task is allowed to store an answer at all.

That ordering makes the counterexample useful. A test that deletes the cache entry before revoking access would never exercise a warm but forbidden result. The [row-security documentation](https://www.postgresql.org/docs/18/ddl-rowsecurity.html) explains why these checks use a non-owner role without `BYPASSRLS`.

## State the moment your permission promise covers

This function checks access and revisions together in one read statement. Its promise applies to that statement's visible database snapshot.

A grant can change after validation and before a response is sent. The transaction does not hold a permission lock through the network exchange. It cannot recall text already sent to a model provider or another client.

If your product promises a stronger revocation boundary, define how validation and delivery coordinate. Adding one more permission query still leaves a time interval after that query. PostgreSQL's [transaction isolation documentation](https://www.postgresql.org/docs/18/transaction-iso.html) helps distinguish a consistent snapshot from a promise about later changes.

## Keep the other dependencies in view

Checking cited sources does not detect every change that might alter an answer. A newly added document could change retrieval even when all old citations remain unchanged. Track a revision for the document collection and retrieval policy as part of the contract.

The fixture's contract number stands in for such caller-supplied versions. It does not discover a changed prompt, provider model alias or tool schema. The application must advance those identities when their behavior changes.

Expiry is still useful for retention and forgotten dependencies. It cannot replace authorization: an answer with fifty minutes left on its TTL can become forbidden now. This fixture does not test expiry, distributed invalidation, cache encryption or semantic similarity matching.

Also keep application result caching separate from provider prompt caching. [OpenAI's prompt-caching documentation](https://developers.openai.com/api/docs/guides/prompt-caching#does-prompt-caching-affect-output-generation) describes reuse of a matching input prefix while the model generates a new response. It does not make a previously saved application answer current or authorized.

The practical check is simple to describe: leave an old value warm, change something it depended on, then ask whether the application still returns it. Start with the changes your product says must matter. A passing lookup test is only the beginning of that investigation.
