A coding agent finishes its review. The process exits successfully. Its summary says the tests passed.

Which code did those tests check? Did the agent inspect the same revision? Did the check finish, or did the workflow hide its failure? A convincing paragraph cannot answer those questions by itself.

Claude Code can run non-interactively in CI. The useful engineering work is deciding what that run may do, how its result is checked, and which evidence a reviewer receives before accepting a patch.

This guide develops that boundary with a small Rust fixture. It tests the rules for preparing an advisory review packet. It does not run Claude, call a provider, or claim a measured improvement in model review quality.

## Separate the proposal from the evidence

An agent's findings are a proposal for a reviewer to investigate. Test results are observations from an execution. Keep those inputs separate.

For a database patch, the review might flag a connection held during a remote call. A controlled fixture can test whether another request makes progress before that call finishes. Another fixture can check a stale write's affected rows. The findings help direct attention; the fixtures establish their specific observations.

A model-generated `tests_passed: true` field should not become the CI result. The component that ran the verification must supply that result through a path the review cannot rewrite.

The [skills guide](/blog/claude-code-skills-guide) shows how to package the investigation. A reusable procedure still needs evidence tied to the change it inspected.

## Decide which source the review is about

Record the candidate revision, its base, the revision actually verified, and the protected requirement harness. The harness is the independently maintained test code that checks the important contract.

A pull-request head and a synthetic merge revision can differ. Decide which one each job checks and describe that relationship. Do not compare two differently defined revisions and silently treat their results as interchangeable. The [PR head and merge SHA investigation](/blog/the-test-passed-on-the-wrong-commit) explains that distinction.

A commit identifier alone also does not describe uncommitted edits. The verification adapter must establish which tree ran, including generated inputs that affect the result. A process that changes files and then reports the unchanged HEAD has not established that the committed tree passed.

The fixture below uses fixed synthetic source identities. Its `TrustedRun` values stand in for observations collected by a protected CI adapter. It does not authenticate a GitHub artifact or implement that adapter.

## Restrict the review job before invoking Claude

Start with the smallest useful job: inspect a candidate and produce findings. Keep repository writes, merge actions, and production credentials out of that worker.

The [complete Rust source](https://github.com/mehdiakiki/mehdi-cz/blob/content/ai-writing-evidence-2026-10-31/experiments/rust-backend/tests/agent_review_evidence.rs) includes this command construction:

```rust
let mut command = Command::new("claude");
command.args([
    "--bare",
    "--print",
    "Read ci-review/instructions.md and review the candidate files. Return findings for human review.",
    "--model",
    model,
    "--tools",
    "Read,Grep,Glob",
    "--allowedTools",
    "Read,Grep,Glob",
    "--disallowedTools",
    "mcp__*",
    "--max-turns",
    "8",
    "--output-format",
    "json",
    "--json-schema",
    schema,
]);
```

The `model` value comes from the runner's selected configuration. The `schema` value describes the proposal's summary and finding fields in the full fixture. The code constructs a command; it does not execute it. The instruction file would be supplied by the trusted workflow, rather than taken from an unreviewed change.

The [CLI reference](https://code.claude.com/docs/en/cli-reference) distinguishes the flags. `--tools` selects built-in tools; `--allowedTools` pre-approves use. The built-in selection does not remove MCP tools, so this example also denies `mcp__*`. `--bare` avoids automatically loading the host's project customizations.

Those flags are one layer. Enforce file and process access in the execution environment too. A review worker can use an isolated candidate snapshot mounted read-only, limited credentials, and a separate directory for its bounded output. Repository text is material to inspect, including when it contains instructions aimed at the agent.

Keep the project's configured runner selection and execution rules. Adding an AI review does not require changing where deterministic builds and tests run.

## Check that the run actually produced a result

A runner should distinguish a completed review, an interrupted run, a tool denial, a provider failure, and output that does not match the expected schema.

Anthropic's [programmatic usage guide](https://code.claude.com/docs/en/headless#get-structured-output) describes the JSON response envelope. When a schema is requested, verify that `structured_output` exists before reading it. Absence must not turn into an empty finding list.

The Rust fixture's `AgentRun` contains a process outcome, a completion outcome, and normalized proposal bytes. A real adapter must derive those outcomes from the pinned CLI or SDK protocol. The tests deliberately do not claim to verify that vendor-specific parsing.

Put an overall deadline and an output byte limit around the process as well. A turn limit is not a wall-clock budget. Capture stderr separately, preserve why a run stopped, and clean up child work when cancellation requires it. A pipe connected to an unbounded collector merely moves the memory problem.

For a retry, keep the candidate identity fixed. Record each attempt and its stop reason. If a new commit arrives, schedule a new review rather than relabeling the old one.

## Require independent checks before presenting a clean packet

This part of the fixture checks trusted source identity and verification state before interpreting the proposal:

```rust
if evidence.source_sha != candidate {
    return Err("verification belongs to a different source revision");
}
if evidence.harness_sha != protected_harness {
    return Err("verification used a different requirement harness");
}
for required in ["build", "tests", "contract-fixtures"] {
    let matching: Vec<_> = evidence
        .checks
        .iter()
        .filter(|(name, _)| *name == required)
        .collect();
    if matching.len() != 1 || matching[0].1 != CheckState::Passed {
        return Err("required verification is missing, ambiguous, or unsuccessful");
    }
}
if !agent.exit_success || !agent.completed {
    return Err("agent run did not complete successfully");
}
```

The named checks are a local policy for the example. They must each appear exactly once and pass. A failed, missing, skipped, or ambiguous check leaves the packet incomplete, even if the model's summary says everything is ready.

The protected harness identity matters when AI edits tests alongside the implementation. A new implementation and a new test can agree on the same wrong behavior. Keep requirement cases outside the candidate's authority, and review changes to those cases as changes to the contract.

That does not make the harness a complete specification. A passing case proves the observation it checks. It does not establish every business rule or every possible execution order.

After the evidence checks, the fixture parses a bounded proposal with unknown fields rejected. It limits summary size, finding count, finding size, and relative source locations. Those limits make the downstream artifact manageable. They do not establish that a finding is true.

The result is a review packet for a person. The function does not merge code, approve a pull request, or publish a comment.

## Keep publishing under a different authority

A worker that can read files is not a read-only system if it also posts comments or changes pull requests. Publishing is a separate write operation.

A publisher can receive the validated packet and narrowly scoped credentials. Show the reviewed revision beside the findings. If the pull request moves, mark the old review as belonging to its original revision and obtain the evidence the current candidate needs.

Rechecking the head before posting can detect a change. It does not make posting a comment atomic with every later push. Keep revision identity in the review itself, and leave merge preconditions to the repository's actual checks and rules.

This separation also gives failure a clear place to stop. Invalid output can remain an inspectable artifact without becoming a public “clean review.”

For GitHub integration details, use the [official Claude Code GitHub Actions documentation](https://code.claude.com/docs/en/github-actions) with your pinned action and runner configuration. The policy fixture here is not a complete workflow installation.

## Make confident wrong results fail the gateway checks

The accompanying Rust tests use synthetic proposals and trusted-run stand-ins. Their expected outcomes come from the evidence rules:

| Input                                                                | Required outcome           |
| -------------------------------------------------------------------- | -------------------------- |
| Matching source, protected harness, completed checks, valid proposal | Prepare an advisory packet |
| Passing results for an older source                                  | Reject the packet          |
| A different requirement harness                                      | Reject the packet          |
| Confident review text with a failed or skipped required check        | Reject the packet          |
| Missing or duplicate required results                                | Reject the packet          |
| Successful process exit without completion                           | Reject the packet          |
| Model JSON adding its own verification fields                        | Reject the proposal schema |
| Truncated output, excessive output, or an invalid source location    | Reject the proposal        |

The fixture also accepts a valid finding and an empty finding list when the independent requirements are met. A gateway that rejects every input would otherwise look successful on a collection of negative cases.

The command-construction test inspects arguments without spawning Claude. The policy tests exercise normalized inputs without calling GitHub. Together they check the local acceptance rules, not provider conformance or model accuracy.

For live review evaluation, use changes with known failures, correct candidates, and incomplete evidence. Record the candidate, harness, prompt or skill revision, CLI and model identities, tool actions, and findings. Judge missed bugs and invented findings separately.

## What changes when the agent edits code?

Keep the editing workspace separate from the immutable candidate being verified. Commit or otherwise identify the proposed tree, run the existing checks against that tree, and bind the review to it.

An agent can help investigate a failed check and propose the next change. It should not make an unsuccessful check disappear by changing workflow reporting or weakening an assertion whose requirement still applies.

When review automation becomes faster, human review can become the next queue. Measure how long it takes to reach an understood decision, including reproduction and corrections. More generated summaries are useful only when they help that work.

I would accept the automation once its boundaries are inspectable: which source it reviewed, which independent checks ran, how it handled an unfinished result, and what authority could publish the outcome. The generated review then has a clear role in a decision a person can assess.
