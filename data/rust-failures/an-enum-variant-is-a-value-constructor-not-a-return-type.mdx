An enum variant can appear after `::`, look like a constructor, and carry fields, yet it does not automatically become a separate type. Writing a variant where Rust expects a type produces E0573.

The [failing fixture](/rust-failure-atlas/evidence/RFA-562/fail.rs) declares `fn initial() -> State::Ready`. `State::Ready` constructs one value of type `State`; it is not a return type.

## The enum is the sum type

`State` describes the complete set of variants admitted by the value. A variable of type `State` may hold `Ready` now and `Waiting` later after reassignment.

The [repaired fixture](/rust-failure-atlas/evidence/RFA-562/fixed.rs) returns `State` and produces `State::Ready` in the body. The signature and expression now occupy their proper roles.

The [official E0573 page](https://doc.rust-lang.org/error_codes/E0573.html) shows this distinction directly: return the enum type, then construct the desired variant as a value.

## Unit and tuple variants are constructors in the value namespace

A unit variant such as `State::Ready` is a value. A tuple variant such as `Message::Data(bytes)` acts like a constructor function. A struct-like variant uses record construction syntax.

All create values of the enclosing enum. The Reference documents these forms under [enumerations](https://doc.rust-lang.org/reference/items/enumerations.html).

Rust has separate namespaces for types, values, macros, and lifetimes. The [namespaces Reference](https://doc.rust-lang.org/reference/names/namespaces.html) helps explain why a familiar path may resolve but still have the wrong kind for its position.

## A function returning one variant still returns the enum

The `initial` function always returns `Ready` today. Its type remains `State`. Callers can pattern match, compare, or pass the result wherever a state is expected.

The implementation may later choose `Waiting` without changing its signature. If returning only Ready is an invariant that callers should rely on at compile time, the enum may be too broad.

## Typestate uses distinct types for compile-time state

A protocol builder can use marker types such as `Connection<Ready>` and `Connection<Waiting>`, where `Ready` and `Waiting` are actual structs. Methods then exist only for appropriate states.

This is a different design from enum variants. It moves state transitions into the type system and can increase generic complexity and code generation.

I use an enum for runtime alternatives and typestate when compile-time exclusion of operations gives enough safety value to justify the API cost.

## Newtypes can prove a validated subset

Sometimes a function should return a value known to be ready while the wider state remains runtime data. A public `ReadyState` wrapper with a checked constructor can represent that proof.

Returning `Result<ReadyState, StateError>` communicates validation. Pretending `State::Ready` is already such a type skips the representation and transition design needed to support the guarantee.

## Pattern positions accept variants

Variants are also used in patterns:

```rust
match state {
    State::Ready => start(),
    State::Waiting => wait(),
}
```

This may contribute to the confusion because the same path appears in expression and pattern contexts. Neither makes it a type. I identify the syntactic position first when reading an “expected type” diagnostic.

## Serialization tags do not create Rust subtypes

A JSON or protocol schema may call each variant a separate message kind. Derive macros can encode and decode those tags, but the in-memory Rust value still has the enclosing enum type. If one variant carries a rich independent schema used elsewhere, I may define a separate payload struct and place it inside the variant. That payload is a real type; the variant remains the constructor connecting it to the sum. This separation gives reusable fields without pretending runtime discriminants are compile-time subtyping.

## My E0573 checklist

- Is the compiler currently expecting a type, value, pattern, or module?
- Does the path name an enum variant rather than the enum?
- Should the signature return the enclosing enum?
- Is “always this variant” merely current behaviour or a required proof?
- Would a distinct typestate marker or validated newtype model that proof?
- Are callers expected to handle runtime alternatives through match?
- Did an import make a value name look like a type name?
- Does the repaired API preserve future implementation choices?

The core principle is that variants inhabit an enum; they do not each define a type. I return the enum for runtime state and introduce real types only when the API needs compile-time state evidence.
